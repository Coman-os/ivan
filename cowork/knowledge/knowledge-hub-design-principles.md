## 1. Core Principles

### 1.1 Channel-First Transparency

**Принцип:** Каждая роль получает информацию через свой канал, но источник один.

**Каналы доставки:**
- **Knowledge Hub (Git)** — Source of Truth
- **Google Drive** — Collaborative workspace, PDF-экспорты
- **Email / Telegram** — Push notifications
- **PDF / Reports** — Snapshot exports

**Правило:** Канал ≠ Source of Truth. Канал = презентационный слой.

**Следствие:** Если роль не имеет доступа к Knowledge Hub, она должна получать ВСЮ релевантную информацию через свой канал.

---

### 1.2 SSOT (Single Source of Truth)

**Принцип:** SSOT определяется по ТИПУ данных, не по системе.

| Тип данных | SSOT | Каналы доставки |
|------------|------|-----------------|
| Структурированное знание | Knowledge Hub (.md) | GDrive (PDF), Email |
| Количественные метрики | Таблицы (Excel/Sheets) | Knowledge Hub (ссылки) |
| Первичные данные | Канал сбора (транскрипты, формы) | Knowledge Hub (обработка) |
| Визуальные материалы | Google Drive | Knowledge Hub (ссылки) |

**Антипаттерн:** Один файл для всего. SSOT = много источников, каждый для своего типа.

**Правило:** Не дублировать контент между каналами. Экспортировать из SSOT.

---

### 1.3 Knowledge Core vs Operations

**Принцип:** Разделение по частоте изменений, переиспользованию, привязке ко времени и состоянию.

| Критерий | Knowledge Core | Operations |
|----------|----------------|------------|
| **Частота изменений** | Редко (кумулятивно растёт) | Часто (каждая встреча/неделя) |
| **Переиспользование** | Да — полезно через год или другой команде | Нет — полезно только этой команде сейчас |
| **Привязка ко времени** | Не привязано к конкретному периоду | Привязано к неделе, кварталу, инциденту |
| **Привязка к состоянию** | Истинно независимо от текущего статуса | Актуально только при текущем состоянии |
| **Тип знания** | Причинные связи, инженерные факты, решения с обоснованием | Рекомендации, рефлексивные вопросы, статусы, метрики |
| **Вопрос для проверки** | Буду ли я использовать это снова? | Это произошло один раз? |
| **Примеры** | Методология, шаблоны, причинные модели, проверенные/отвергнутые решения | Встречи, отчёты, трекеры, текущие рекомендации |

**Decision:**
- Если контент переиспользуется и не привязан ко времени/состоянию → Knowledge Core
- Если контент уникален (событие, встреча) или привязан к текущей ситуации → Operations

**Связь:** Knowledge Core — результат рефлексии над Operations (извлечение паттернов из событий). И одновременно — источник рефлексии (база для интерпретации новых событий). Operations → рефлексия → Core → следующие Operations интерпретируются глубже.

## 2. Role Coverage Matrix

**Принцип:** Каждая роль видит всю релевантную информацию через свой канал.

### 2.1 Шаблон матрицы

| Роль | Основной канал | Что видит | Периодичность |
|------|----------------|-----------|---------------|
| **Executive (CEO/COO)** | Email / Push | Summary, критические метрики | Еженедельно |
| **Manager** | Collaborative (GDrive) | Dashboard, детали | По запросу |
| **Team Member** | Knowledge Hub | Полный контекст | Постоянно |
| **External Partner** | Public channel | Filtered view | По договорённости |

### 2.2 Правило полноты

**Тест:** Может ли роль X выполнить свою работу, используя только канал Y?

Если нет → добавить недостающую информацию в канал Y.

## 3. Information Flow Design

### 3.1 Базовый flow

```
Raw Input → Knowledge Hub (SSOT) → Transformation → Channels → Roles
```

**Этапы:**
1. **Raw Input** — первичные данные (транскрипты, формы, метрики)
2. **Knowledge Hub** — обработка, структурирование, связывание
3. **Transformation** — адаптация под роль (агрегация, фильтрация)
4. **Channels** — доставка через канал роли
5. **Roles** — потребление информации

### 3.2 Типы трансформации

| Роль | Трансформация | Пример |
|------|---------------|--------|
| **Executive** | Агрегация + Summary | 9 команд → 1 dashboard |
| **Manager** | Фильтрация по области | Только своя команда |
| **Team** | Полный контекст | Все детали |
| **External** | Фильтрация по доступу | Только публичное |

## 5. Document Lifecycle: Composite → Decomposed

**Принцип:** Знание естественно начинает жизнь как составной документ (composite) и декомпозируется в модульную структуру по мере роста числа потребителей.

### 5.1 Lifecycle

| Стадия | Состояние | Триггер перехода |
|--------|-----------|------------------|
| **Composite** | Один файл, типы знания перемешаны. Нормально для стадии синтеза. | Документ обслуживает >1 потребителя ИЛИ превышает ~300 строк |
| **Decomposed** | Модульная структура: отдельные файлы по типу/домену/роли | — |

### 5.2 Триггеры декомпозиции

Документ нужно декомпозировать, когда:
1. **>1 потребитель** — разные роли/агенты читают разные части одного файла
2. **Размер** — файл превышает ~300 строк и содержит логически независимые блоки
3. **Разная частота изменений** — части файла обновляются с разной периодичностью

### 5.3 Правила декомпозиции

- Выделяй по **роли** (для кого), не по формату (таблица vs текст)
- Сохраняй **один source of truth** — декомпозированные файлы ссылаются друг на друга, не дублируют
- **Не декомпозируй преждевременно** — в момент синтеза разделение убивает мысль (см. knowledge-core-structure.md §3а)

### 5.4 Связь с Knowledge Core

В Knowledge Core аналогичный lifecycle описан для genesis-документов (§3а knowledge-core-structure.md: Draft → Approved → Indexed). Этот принцип обобщает паттерн: **любой** документ в Knowledge Hub проходит путь Composite → Decomposed, не только genesis.

## 6. Card Recon — автономность H2-секций для экономии контекста агента

**Принцип:** Каждый файл в Knowledge Hub устроен так, чтобы агент мог решить «нужен этот файл или нет» по двум Grep-вызовам, без чтения тела документа.

### 6.1 Карточка файла = Назначение + H2-spine

Карточка собирается из двух источников:

1. **Поле `Назначение`** в таблице метаданных — миссия файла в 1–3 предложениях (≤100 слов). Стандарт описан в (внутренний документ).
2. **H2-заголовки** (`^## `) — структурный скелет файла, навигационная карта.

По карточке агент решает:
- **Нет** — файл не релевантен, переходим к следующему. Стоимость = ~5 строк контекста.
- **Да** — определяем релевантную секцию по H2, читаем её через `Read(offset, limit)`. Стоимость = размер одной секции, не всего файла.

**Эффект:** при обходе 20 файлов — ~100 строк контекста вместо 600–1000.

### 6.2 H2 как самодостаточный «скелет» файла

Каждый H2-заголовок:

- **Самодостаточен** — понятен без чтения родительского файла. Не «Подход» или «Принципы», а «Card Recon — автономность H2-секций для экономии контекста агента».
- **Описывает один концепт** — не объединяй несколько идей в один H2.
- **Стабилен** — заголовок не меняется при обновлении тела секции. Если меняется суть — это новый H2.

Внутри секции H3/H4 могут быть короткими, потому что родительский H2 даёт контекст.

### 6.3 Антипаттерны

| Антипаттерн | Почему плохо | Решение |
|-------------|--------------|---------|
| H2 = «Подход», «Детали», «Прочее» | Карточка бесполезна — агент вынужден читать тело | Конкретный H2 с предметом и квалификатором |
| `Назначение` повторяет H1 | Дублирование, не даёт нового сигнала | Назначение объясняет «зачем», H1 — «что» |
| Длинный pre-amble перед H2-шапкой | H2-spine становится неполным (вступление вне skeleton) | Содержательную часть выносить в H2 |
| Мета-инструкции «прочти меня сначала» в теле файла | Это контекст для агента, не для системы знаний | В hooks или skill, не в .md |

### 6.4 Связь с другими принципами

- §1.2 SSOT: карточка не дублирует SSOT, она indexed view над ним.
- §5 Composite → Decomposed: при декомпозиции каждый новый файл получает своё `Назначение` и H2-skeleton.
- §1.3 Knowledge Core vs Operations: для Operations-файлов карточка опциональна (см. §2.0 в requirements.md).

## 7. Anti-patterns

| Anti-pattern | Почему плохо | Решение |
|--------------|--------------|---------|
| **SSOT в нескольких местах** | Рассинхронизация | Один SSOT, остальное — экспорты |
| **Канал без аудитории** | Мёртвый канал | Удалить или переосмыслить |
| **Информация без владельца** | Устаревает | Назначить владельца |
| **Дублирование между каналами** | Рассинхронизация | Экспорт из SSOT |
| **Всё в одном файле** | Сложно поддерживать | Разделить по типам данных |
