**Формат:** conventional commits (`feat`, `fix`, `refactor`, `docs`)

## Правила

- Коммит = завершённая смысловая единица (не «конец дня», не «каждый файл»).
- Тип коммита Claude определяет сам:
  - `feat` — новый файл, раздел, функциональность
  - `fix` — исправление ошибки, опечатки
  - `refactor` — реструктуризация без изменения смысла
  - `docs` — обновление документации, README
- Разбивать по областям не нужно — области видны из путей файлов.
- Смешанные коммиты (несколько областей) — нормально, если изменения связаны.
- Логически независимые изменения — разделять на отдельные коммиты самостоятельно, не спрашивая.

## Scope'ы

Scope — по области репозитория. Конкретные scope-имена команд/проектов задаются в overlay экземпляра; базовые:

| Scope | Когда использовать |
|-------|-------------------|
| `{client}` | операционные файлы экземпляра (данные клиента, конфиг, команды) |
| `{client}/{team}` | файлы конкретной команды |
| `coman-os` | платформа (регенерируется — правится в основном репозитории, не в экземпляре) |
| `docs` | документация, README, навигация |

## Дополнительные правила

- **Перед коммитом накопленных изменений** → `git diff HEAD [файл]` для понимания, что именно изменилось (иначе сообщение получается общим).
- **Итеративные правки одного файла** в рамках одной задачи = один коммит по завершении задачи, а не после каждой итерации.

## Примеры разделения

- Изменения в разных командах → отдельные коммиты.
- Правки документации/навигации → отдельный коммит.
- Метаданные / compliance-фиксы → отдельный коммит.
