## §1. Две области

```
Экземпляр CoMan OS
├── coman-os/                — платформа Coman (методология, принципы, харнесс, skills)
│   → РЕГЕНЕРИРУЕТСЯ экспортёром. Руками в экземпляре НЕ править —
│     правка в основном репозитории, затем пере-сборка.
└── {client}-knowledge-hub/  — знания и авторинг экземпляра (ваше содержимое)
    → здесь вы пишете: команды, встречи, заметки, документы.
```

Определяющий вопрос: **это переиспользуемая методология платформы или содержимое конкретного экземпляра?**

---

## §2. Главный Decision Tree

```
О ЧЁМ документ?
│
├── Методология / принцип / харнесс-правило / skill платформы
│   (переиспользуется любым клиентом, не привязано к данным)
│   → coman-os/  → §3   [правится в основном репозитории, не в экземпляре]
│
└── Знание или работа конкретного экземпляра
    (команды, встречи, заметки, документы, локальные правила клиента)
    → {client}-knowledge-hub/  → §4
```

## §3. Внутри `coman-os/` (для контрибьютора платформы)

```
coman-os/
├── knowledge-core/  — методология и принципы работы со знаниями
├── scl/             — Skill Consistency Layer: reference, workflows, skills, стандарты документов
├── shared/          — схемы (JSON Schema), views, принципы агентов, паттерны
└── tools/           — утилиты (генератор PDF, скрипты)
```

- **knowledge-core/** — принципы «как думать» (универсальные правила работы с объектами знания).
- **scl/** — правила «что делать»: reference-справочники, workflows, skills (`skill-{name}.md`), стандарты оформления, правила размещения (этот документ), карта skills.
- **shared/** — общие ресурсы для агентов и авторинга: схемы форм, views, принципы проектирования агентов.
- **tools/** — исполняемые утилиты.

> В экземпляре `coman-os/` — регенерируемый артефакт. Правки платформенных
> файлов делаются в основном репозитории и приезжают пере-сборкой; локально их
> не редактируют (перезатрёт).

## §4. Внутри `{client}-knowledge-hub/`

- **`teams/{team}/workspace/`** — ручная зона авторинга команды: drafts, заметки, эксперименты, гипотезы, бизнес-кейсы. Плоская папка на старте; подпапки возникают от реальных артефактов, не угадываются заранее. **Синхронизация (pipeline) `workspace/` не трогает** — это ваша зона, автоматика её не перезаписывает.
- **rendered-артефакты** (трекеры, дашборды, выжимки, приезжающие от pipeline) — **руками не править**: они регенерируются при следующей синхронизации. Правится вход (транскрипт, конфиг), не выход.
- **Материалы, не предназначенные команде** (профиль лидера, приватные наблюдения, разбор до встречи с командой) — держать **вне** зоны, которую видит команда: их публикация в командный hub нарушит доверие. Разделение по каналу хранения, не по имени файла.

## §5. Структура папок и масштабируемость

- В папке накопилось **≥10 `.md`** — разбить на подпапки по **смысловой теме** (не по дате/типу). Каждая подпапка получает свой `README.md` с индексом. Менее 3 файлов в подпапке — не создавать (объединить с ближайшей по смыслу).
- Enforcement: hook `post_write_readme_sync` (папка с ≥1 `.md` без `README.md`-индекса → блок).
- Правило размещения фиксируется здесь, не в README. README — индекс содержимого, не носитель правил.

## §6. Правила именования файлов

**Принцип:** filename = поисковый запрос. Инструменты ищут в первую очередь по именам файлов. Имя = сжатая суть; `title`/H1 в шапке = развёрнутое описание (разные роли, не дублирование).

- **Формат:** `kebab-case.md` — строчные буквы, дефисы.
- **Язык:** английский. Транслит запрещён. Человекочитаемое название — в H1 и метаданных.
- **filename vs title:** filename — стабильный ID для ссылок и поиска (не меняется при правках контента); title в шапке — полное описание для человека.
- **Содержит слова для поиска:** включать субъект (домен, проект, кто/что), не только тип. Плохо: `notes.md`. Хорошо: `team-adoption-notes.md`.

**Датированные файлы (встречи, чекины, события):** `YYYY-MM-DD-{что/кто}-{опциональный-маркер}.md`
- Дата — ISO 8601, всегда первой (корректная сортировка).
- Тема содержит субъект: 1-on-1 → имя, регулярная встреча → формат, стратегическая → тема.
- Маркер недели/итерации — в конце, если релевантно (`-w16`, `-q1`).
- Расшифровки встреч живут во внешнем канале хранения, выжимки — в hub. Суффикс `_transcript`/`_summary` не нужен: разделение по каналу, не по имени.

**Примеры:** `2026-04-15-okr-workshop-w16.md`, `2026-03-27-one-on-one-vasily.md`, `2026-02-10-strategy-session-pricing.md`.

**Что не нужно:** нумерация порядка чтения (`01_vision.md` — иерархия папок уже задаёт порядок); тип-суффиксы (`_summary`, `_plan` — тип задаёт папка и метаданные).

**Миграция:** массовая переименовка существующих файлов не проводится — правило применяется к **новым** файлам (переименование даёт ноль пользы при риске сломать ссылки).

## §7. Чек-лист перед размещением

1. **О чём документ?** → платформа (`coman-os/`) или экземпляр (`{client}-knowledge-hub/`)? (§2)
2. **Платформенный файл?** → правится в основном репозитории, не в экземпляре (регенерируется).
3. **Ручное или rendered?** → авторское в `teams/{team}/workspace/`; rendered от pipeline не править.
4. **Есть ли README в целевой папке?** → файл должен быть виден в навигации (иначе hook заблокирует).
5. **Нет ли дубликата контента?** → grep по ключевым терминам. Если правило/определение уже есть в другом файле → ссылка вместо копии (rules.md → «Ссылайся, не повторяй»).
