Decision Tree для выбора инструмента авторинга и обслуживания знаний. Аналогично
тому, как placement-док решает «КУДА положить документ», этот документ решает
**«ЧТО ЗАПУСТИТЬ для задачи»**.

**Покрытие:** 8 платформенных skills (декларация набора и границ ядра).

> ⚠️ **Статус поставки (версия базы 0.1.x):** skill-набор Волны 2 **собран** — базой едут (skill-форма, `.claude/skills/`): `cmn:dialectic-partner` (Mold A), `cmn:close-session` (Mold B: трекер-интерфейс `list_open`/`close_task`, адаптер даёт экземпляр), `cmn:kh-check` (Mold B bulk: универсальные проверки + таксономия из `kh.doc_taxonomy_ref`, Проверка D config-gated), `cmn:pdf` (HTML→PDF, Chrome-primary + опц. Puppeteer). **`cmn:onepager` (+`cmn:onepager-critic`) отложены** (demand-driven: нет consumer'а под partner-demo страницы; вернуть вместе с полем `brand` при спросе). Статус `cleanup-crew` / `knowledge-sync` — в ledger дистрибутива. Карта = **декларация набора и границ ядра**, не список доступных сейчас команд.

> 🔗 **Overlay-скилы клиента в эту карту не входят.** Bespoke-скилы экземпляра (напр. отчётность {client}) живут в `.claude/skills/` под защитой `.baseignore` и в эту (регенерируемую) карту не попадают. Их реестр — `.claude/skills/README.md` самого экземпляра. **Перед созданием нового скилла свериться И с этой картой (платформа), И с overlay-реестром экземпляра** — чтобы не продублировать существующую способность. Раскладка унифицирована: все capabilities = скилы в `.claude/skills/` (было `.claude/commands/`); финализация именования платформенных скилов — при их отгрузке (Волна 2).

**Что НЕ входит в clean-core** (по границам дистрибуции):
- *операционные скилы клиента* (задачи, внешний трекер, бэклоги, встречи, синхронизация проекта) → overlay экземпляра как `{client}:`;
- *движки* (извлечение знаний, приоритизация, матчинг) и *OKR-агенты-продукты* → не едут (IP);
- *go-to-market* (пресейл, контент, стратегия, sales deck) → не едут.

## Namespace-конвенция (три пространства имён)

| Namespace | Что это | Где живёт | Обновление |
|---|---|---|---|
| `cmn:<skill>` | **платформа Coman** (ядро) | `.claude/commands/cmn/` | генерируется экспортёром / subtree — **руками не править** (перезатрётся при пере-сборке) |
| `{client}:<skill>` | **bespoke под одного клиента** | overlay: `.claude/commands/{client}/` | правится локально в экземпляре |
| `/<builtin>` | встроенные команды Claude Code | — | не наши |

- Вызов: `/cmn:<skill>` и `/{client}:<skill>`. Префикс сразу говорит происхождение и правило обновления.
- **Агенты** (не slash-команды): платформенные — префикс `cmn-` (`cmn-cleanup-orphan`), клиентские — `{client}-`.
- Клиента в самом имени не повторять (`{client}:team-lifecycle`, не `{client}:{client}-team-lifecycle`).
- **В монорепо (sandbox) платформенные skills остаются без префикса** (bare); экспортёр мапит `bare → cmn:` при генерации clean (Copybara-rename, как для путей слоёв). Конвенция `cmn:` — стандарт дистрибутива, не монорепо.
- Полный стандарт именования (kebab-case, no underscore, ≤64) — agent-design §B7.

## §1. Decision Tree — «Какой инструмент запустить?»

```
Какая задача?
│
├── Качество и связность знаний
│   ├── После правок .md (инкрементально) → cmn:kh-check
│   ├── Найти связи нового документа с базой → cmn:knowledge-sync (→ cmn-kw-reflect + cmn-kw-reweave)
│   └── Полный аудит + автофикс → cmn:cleanup-crew (→ cmn-cc-* агенты)
│
├── Критическое мышление
│   └── Проверка идеи / гипотезы → cmn:dialectic-partner (→ cmn-dialectic-partner agent)
│
├── Публикация
│   ├── Премиальная HTML-страница из .md → cmn:onepager  ⏸ отложен (demand-driven; +critic)
│   └── Готовый HTML → PDF → cmn:pdf
│
└── Сессия
    └── Завершение сессии → cmn:close-session  (base + трекер-адаптер экземпляра, Mold B)
```

---

## §2. Ритм — «Когда что запускать»

| Частота | Инструмент | Триггер |
|---------|-----------|---------|
| После правок .md | `cmn:kh-check` | инкрементальная валидация изменённого |
| При новом документе | `cmn:knowledge-sync` | найти связи с базой |
| Раз в 2 недели | `cmn:cleanup-crew` | полный аудит + автофикс |
| Конец сессии | `cmn:close-session` | завершение работы (base + трекер-адаптер экземпляра) |
| По запросу | `cmn:dialectic-partner`, `cmn:pdf` (`cmn:onepager` + critic — отложены) | контекст задачи |

---

## §3. Цепочки — «Что идёт после чего»

```
{новый / изменённый документ} → cmn:kh-check → (если много проблем) → cmn:cleanup-crew
  (инкрементальная проверка → эскалация на полный аудит)

{новый документ} → cmn:knowledge-sync
  (найти связи нового документа с существующей базой)

cmn:onepager → cmn:onepager-critic
  (упаковал .md в премиальную HTML-страницу → ревью глазами партнёра)

{идея / гипотеза} → cmn:dialectic-partner
  (критическая проверка через интеллектуальное сопротивление)
```

## §4. Skills, вызывающие агентов

| Skill | Агент(ы) | Связь |
|-------|----------|-------|
| `cmn:cleanup-crew` | cmn-cc-orphan, cmn-cc-consistency, cmn-cc-context, cmn-cc-links | Skill оркестрирует 4 агента последовательно |
| `cmn:knowledge-sync` | cmn-kw-reflect, cmn-kw-reweave | Skill оркестрирует 2 агента последовательно |
| `cmn:dialectic-partner` | cmn-dialectic-partner | Skill = интерфейс к агенту |

`cmn:kh-check`, `cmn:onepager`, `cmn:onepager-critic`, `cmn:pdf` — прямые skills без агент-обёртки.

---

## §5. Антипаттерны — «Когда НЕ использовать»

| Ошибка | Правильно |
|--------|-----------|
| `cmn:cleanup-crew` для ежедневной проверки | → `cmn:kh-check` (инкрементальная) |
| `cmn:knowledge-sync` для полного аудита | → `cmn:cleanup-crew` (полный аудит + автофикс) |
| `cmn:kh-check` после рефакторинга 50+ файлов | → `cmn:cleanup-crew` (полный аудит эффективнее) |
| `cmn:onepager` для оценки готовой страницы | → `cmn:onepager-critic` (генератор не оценивает свой output) |
| `cmn:onepager-critic` для сборки страницы | → `cmn:onepager` (critic только оценивает) |
| Править `cmn:`-skill руками в экземпляре | → он регенерируется экспортёром; правка в основном репозитории, затем пере-сборка |
| Вызвать bespoke-скил клиента как платформенный | → он в overlay как `{client}:<skill>`; в ядре только `cmn:` |
