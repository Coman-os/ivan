# §A. Продуктовые агенты

Принципы для самостоятельных LLM-агентов (`products/`). 12 принципов + чек-лист.

---

## Принцип 1: Специализация — один агент, одна задача

Каждый агент закрывает ровно один gap в цикле. Overlap между агентами недопустим.

**Если → тогда:**
- Если задача «немного выходит за границы» агента → это handoff, а не расширение scope
- Если два агента делают похожее → оставь один, второй переведи в archived
- Если агент «умеет всё» → это оркестратор, не продуктовый агент

---

## Принцип 2: Три слоя контекста — явные, всегда

Каждый промпт агента явно разделяет три слоя по природе данных. Агент не читает файлы напрямую — он получает собранный контекст.

| Слой | Что входит | Природа | Инфра сейчас | Инфра промышленная |
|------|-----------|---------|--------------|-------------------|
| **Universal Core** | Онтология, принципы, схема графа | Неизменяемый | Часть промпта | Память процесса (~0ms) |
| **Client Core** | Setup-файлы, справочники команд, глоссарии, профиль клиента | Раз в квартал | Читается при запуске | Кеш TTL 7-30 дней (~5ms) |
| **Operations** | Транскрипт, history-log, метрики, трекер | Каждая встреча | Читается каждый раз | Hybrid search (~150ms) |

**Правила написания:**
1. Universal Core — в промпте, ссылка на глоссарий как SSOT онтологии
2. Client Core — явная секция с TTL и fallback-цепочкой при отсутствии файла
3. Operations — явная секция, без кеша, fallback для каждого источника
4. Агент не знает источник данных — только получает собранный контекст

**Почему это важно сейчас (до промышленной инфры):** структура промпта определяет, что можно кешировать без переписывания агента. Если слои не выделены — при переходе на промышленную инфру придётся переписывать промпт.

**Cache-aware ordering (физический порядок токенов в промпте):**

Prompt cache работает на префиксе. Промпт строится так, чтобы стабильные части шли **до** волатильных — иначе каждый run = cache miss.

| Позиция | Что | Изменчивость |
|---|---|---|
| 1 (начало) | System role + Universal Core + tool definitions (детерминированный порядок) | Месяцы |
| 2 | Client Core (setup, glossary, team-directory) | Квартал |
| 3 | Stable Operations context (history-log за фиксированный период) | Дни |
| 4 (конец) | Текущая выжимка / транскрипт + timestamp + request_id | Каждый run |

**Если → тогда:**
- Если в промпте есть `current_time` / `run_id` / `today_date` → они в **конце** промпта, не в системной роли
- Если tool definitions сериализуются — порядок tools **детерминированный** (alphabetical / fixed list), не Python dict insertion order
- Если Client Core рассыпан между несколькими файлами → конкатенировать в стабильном порядке (одна и та же последовательность каждый run)
- Если cache hit rate < 50% по логам → искать волатильные значения в верхней части промпта

**Анти-паттерны:**
- `f"Сейчас {datetime.now().isoformat()}, выполни..."` в начале — кеш-killer
- Динамический список tools в зависимости от run-context — fragmentation кеша
- Compaction summary, переписываемая каждый turn — кеш-miss каждый turn

**Что логировать:** `cache_read_input_tokens` / `cache_creation_input_tokens` из API response — мониторить по сессии и по агенту. Cache hit rate ниже baseline → структура промпта деградировала.

## Принцип 3: Онтология — в Universal Core, факты — в Operations

Определения терминов, типы сущностей, цепочки трансформаций — никогда не переопределяются данными из транскрипта или истории.

**Если → тогда:**
- Если команда использует термин в своём смысле → агент использует определение из глоссария, не из транскрипта
- Если в Operations появился новый тип сущности → это кандидат в глоссарий, не расширение Operations
- Если принцип применим к любому клиенту → Universal Core. Если специфичен для одного клиента → Client Core

**Связь с лестницей мест (Принцип B2).** Выбор слоя контекста для нового знания подчиняется той же логике, что лестница мест перед memory: **специфичный слой > универсальный**. Сначала проверяй, не помещается ли знание в Operations (самый специфичный), потом Client Core, и только если универсально для всех клиентов — Universal Core. Это применение бритвы Оккама к выбору слоя: не плоди универсальные сущности из единичного факта.

## Принцип 4: Явные handoff — пользователь всегда знает о переходе

При передаче контекста между агентами — структурированный handoff, не молчаливый.

**Формат:**
```
[HANDOFF: {from_agent} → {to_agent}]
REASON: {почему}
CONTEXT: {структурированный контекст}
EXPECTED ACTION: {что должен сделать следующий агент}
[/HANDOFF]
```

**Анти-паттерны:**
- Scope creep — агент делает работу другого агента
- Silent handoff — переход без уведомления пользователя
- Context loss — следующий агент не получил нужный контекст
- Circular handoff — агенты передают задачу друг другу по кругу

## Принцип 5: Версионирование — semver, миграция обязательна при breaking change

| Тип изменения | Версия | Документация | Миграция |
|--------------|--------|-------------|---------|
| Баг-фикс, уточнение формулировки | vX.Y.**Z+1** | Changelog | Нет |
| Новая функция, новый шаблон | vX.**Y+1**.0 | Changelog детальный | Опционально |
| Изменение формата вывода, удаление секции | v**X+1**.0.0 | Changelog + Migration Guide | Обязательна |

**Тест наблюдаемости (decision-процедура перед таблицей).** Таблица — это lookup по типу изменения; сначала реши, *версия ли это вообще*, одним вопросом к потребителю сущности: «заметит ли он разницу — и обязан ли он что-то сделать иначе?».

- **Не наблюдаемо снаружи** (внутренний рефактор, переименование переменной, правка комментария) → **не версия**, только коммит.
- **Наблюдаемо, обещание то же** (стало чище/точнее/меньше ошибается при том же входе/выходе — «качество исполнения») → **PATCH**. Качество при неизменном контракте — это *не* «ничего» и *не* minor.
- **Обещание расширилось**, обратно-совместимо (новый шаг, новое поле на выходе) → **MINOR**.
- **Обещание сломалось** (иначе вызывать / читать выход) → **MAJOR**.

Граница идентичности сущности проходит по **контракту** (вход/выход/порядок шагов), не по конкретной внутренней реализации: оркестратор версионируется при смене контракта оркестрации, не при правке нутра одного шага (у того своя version). Правило симметрично для skill'а, агента и pipeline-оркестратора.

**Правило:** experimental → production только после тестирования на реальных данных.

## Принцип 6: Signal Density — каждое слово в промпте управляет поведением

Промпт — это код. Лишнее слово создаёт лазейку. Нечёткая формулировка = класс ошибок.

**Если → тогда:**
- Если формулируешь правило → проверь: можно убрать хоть одно слово без потери смысла?
- Если видишь «или», «рекомендуется», «по возможности» → это лазейка. Замени на точную формулировку
- Если агент систематически делает что-то не то → сначала найди лазейку в формулировке, потом правь

**Пример:** «цитата или пересказ» → агент уходит от дословного цитирования. Убрать «или пересказ» — класс ошибок исчезает.

## Принцип 7: Структура промпта — обязательные секции

Каждый продуктовый агент содержит секции в этом порядке:

| # | Секция | Что включает |
|---|--------|-------------|
| 1 | Роль и идентичность | Кто агент, позиция в цикле, тон |
| 2 | Universal Core | Онтология, принципы (ссылки на SSOT, не копии) |
| 3 | Client Core | Файлы клиента, TTL, fallback-цепочки |
| 4 | Operations | Динамические источники, fallback при отсутствии |
| 5 | Цель и задачи | Что делает агент по объектам анализа |
| 6 | Алгоритмы | Пошаговые инструкции |
| 7 | Формат вывода | Шаблоны артефактов |
| 8 | Ограничения | Что агент НЕ делает, кто отвечает вместо него |

**Отступление от порядка — только с явным обоснованием в changelog.**

## Принцип 8: Агент не оценивает свой output

Self-evaluation провалена. Агент-генератор и агент-оценщик — разные агенты.

**Если → тогда:**
- Если нужна проверка качества → отдельный evaluator-агент или human-in-loop
- Если агент «проверяет себя» → это иллюзия валидации
- Если нужно **сократить/упростить** собственный output → тоже свежий контекст, не тот же агент. Минимализм автора заякорен на рассуждении, через которое он прошёл — лишнее не видно, потому что для автора оно обосновано путём. Simplification, как и evaluation, требует fresh context. (Различать: evaluation = «вот слабое место», simplification = «вот это лишнее, режь» — разные акты.)

**Граница изоляции — по онтологической природе агента, не по фазе работы.** «Свой output» проходит не между research и compilation, а между агентами разной природы. Агент, моделирующий **целостное синхронное человеческое суждение** (например, агент-аналитик, воспроизводящий неделимый акт оценки специалиста), **не делится** на discovery/verification фазы и не получает information-isolation внутри себя: сбор фактов и вывод у него — единый акт суждения, разделение разрушит целостность, которая и есть смысл такого агента. Изоляция/независимая верификация живёт **только на границе агент-суждение → downstream-инструмент**: узкий инструмент получает результат (например, рекомендацию + снапшот состояния), но **не** обоснование агента-суждения — иначе анкорится на чужой уверенности.

- Если агент = целостное суждение → не делить по фазам, изоляция только на выходе в инструмент другой природы
- Если агент = узкий инструмент → изоляция от upstream-reasoning уместна (передавать факты, не обоснование автора)

Эта граница — уточнение общего harness-паттерна «find/grade разделены» (там два типа работы с противоположными целями recall vs precision). Базовый паттерн не различает «агент=инструмент» vs «агент=целостное суждение»; это различение — существенное: разделять целостное суждение на фазы так же вредно, как сливать раздельный процесс в монолит.

## Принцип 9: MVP Blueprint — минимальная безопасная форма до расширения автономности

Новый агент проектируется как MVP — минимальная безопасная форма, доказывающая ценность на реальных данных. Расширение автономности только после прохождения eval'ов на этой форме.

**Если → тогда:**
- Если задача «нужен агент для X» → начинать с answer-only или draft-only, не с автономного действия
- Если хочется добавить N tools «на всякий случай» → каждый tool требует обоснования в MVP scope
- Если нет evals на текущей форме → расширять автономность запрещено

**Обязательный MVP Blueprint (заполняется перед первой строкой системного промпта):**

| Секция | Что включает |
|---|---|
| **Objective** | Что агент делает и для кого. Одна фраза. |
| **Decomposition check** | Монолит или разделение на изолированные агенты/фазы. См. процедуру ниже. Default — монолит для синхронного человеческого суждения; разделение только при явном триггере, записанном здесь. |
| **MVP scope** | Минимальная полезная форма, явные assumptions, non-goals, что отложено |
| **Autonomy level** | answer-only / draft-only / approval-gated / autonomous-within-policy |
| **Risk classes** | См. таблицу ниже. Какие классы агент трогает — все перечислить |
| **Permission matrix** | Для каждого класса риска: разрешено / draft+approval / запрещено |
| **Core loop** | Шаги: instructions → model call → tool/action → validation → permission → execution → observation → repeat/finish |
| **Budgets** | step / tool-call / time / token / cost — численно |
| **Validation** | Что доказывает «done» — измеримый сигнал, не «по ощущениям» |
| **Evals** | Минимум 3 категории из Принципа 10 — обязательно перед launch |
| **Launch path** | shadow-mode / pilot scope / metric thresholds для расширения автономности |

**Автономия (`Autonomy level`) градуирована и сцеплена с верификацией (in→on→out).** Уровни `answer-only / draft-only / approval-gated / autonomous-within-policy` — это спектр human-**in**→**on**→**out**-the-loop; автономия **зарабатывается** подъёмом по лестнице доказательства (fidelity → owner-confirm → upstream/independent-check → intervention-confirmed), не выдаётся авансом. Три уточнения, чтобы автономия не была одним рубильником на агента:
- **Per-фаза** — у агента может быть несколько петель (строит / решает / действует в мире); каждая настраивается отдельно. Автономный «писатель» может кормить human-gated «решателя» — не противоречие.
- **Per-stakes** — даже при общем `on` отдельные классы вывода остаются `in` навсегда (необратимое действие, эскалация, флаг недостоверных данных). Автономия привязана к классу вывода, не к агенту целиком.
- **Обратимость (не храповик)** — при входе в неверифицированный режим (новый класс задач/данных, где eval'ы ещё не сошлись) автономия **падает обратно к `in`**. Уровень контекстен к тому, верифицирован ли режим, а не выдан раз навсегда.

> Полную переиспользуемую матрицу «лестница доверия ⊗ autonomy» выносить в этот принцип — при 2-м агенте с градуированной автономией (пока держим как лёгкий захват).

**Decomposition check — процедура (2 вопроса, ответ фиксируется письменно в blueprint):**

Реализует границу из [Принципа 8](#принцип-8-агент-не-оценивает-свой-output) на этапе конструирования. Решает: монолит или разделение на изолированные агенты/фазы.

1. **Моделирует ли агент целостное синхронное человеческое суждение?** (единый акт оценки специалиста на встрече: «что в ситуации» + «что делать» — неделимо). → если да, **default = монолит**. Изоляция/независимая верификация — только на выходе в downstream-инструмент другой природы (агент-суждение → узкий инструмент: инструмент получает результат + снапшот, но не обоснование агента).

2. **Сработал ли хоть один триггер разделения?**
   - (а) **референсный человек сам работает в фазы** — наблюдение → отложенная рефлексия (например, квартальная стратегия, не синхронная встреча);
   - (б) **«единый» агент склеил несколько режимов мышления** — фасилитатор / методолог / стратег; разделение здесь *уточняет* модель человека, не нарушает её;
   - (в) **вывод дорогой/необратимый, нужна точка adversarial-verify** — реструктуризация, эскалация; холизм сознательно разменивается на верифицируемость (у монолита нет промежуточного артефакта для проверки).

   → если да, **делить**, и в blueprint записать: *какой триггер* сработал и *что разменяли* (holistic ↔ верифицируемость / точность модели).

**Критерий — верность референсному человеческому процессу + цена ошибки, НЕ «целостное суждение = всегда монолит».** Неделимость — дефолт для *синхронного* суждения, не свойство агента-суждения как такового.

**Антипаттерн в обе стороны:**
- Делить синхронное суждение → теряем holistic judgment.
- Сливать раздельный процесс в монолит → теряем верность референсу + проверяемость.

**7 классов риска (по убыванию опасности):**

| Класс | Примеры действий | Дефолт permission |
|---|---|---|
| 🔐 **privileged** | Изменение прав, ключей, identity; чтение защищаемого IP-слоя репозитория | Запрещено или approval + strong auth |
| 💥 **destructive** | `rm`, drop table, force-push, перезапись истории | Запрещено или approval + recovery plan |
| 💰 **financial** | Push в трекер с биллингом, оплаты | Approval + strong auth |
| 📤 **external** | Send to client, Slack, email, публикация во внешнее хранилище | Draft + approval |
| ✍️ **write** | Локальная запись в репозиторий, обновление трекеров | Авто внутри scope, approval вне |
| 📝 **draft** | Генерация артефакта без сохранения / черновик | Авто |
| 👁️ **read** | Чтение файлов, search, query | Авто внутри scope |

**Правило:** Если scope позволяет читать защищаемый IP-слой репозитория — это уже **privileged**. Если push во внешний трекер — это **external** + потенциально **financial** (биллинг времени).

**Анти-паттерны:**
- «Multi-agent orchestration с самого начала» → одиночный агент с MVP scope сначала, decomposition только после measurable failures
- «`execute_shell` как универсальный tool» → узкие типизированные tools с явным risk class
- «Permission через текст в промпте» → permission enforcement обязан быть в коде/hook'е, не в формулировке

## Принцип 10: Eval-категории — минимум до launch

Агент не выходит в production без покрытия eval'ами по нижеперечисленным категориям. Self-evaluation (Принцип 8) этого не заменяет.

**10 обязательных категорий eval-кейсов:**

| # | Категория | Что проверяет |
|---|-----------|---------------|
| 1 | **Happy-path** | Типичный вход → корректный выход в формате |
| 2 | **Near-miss** | Граничный случай (пустая выжимка, частичные данные, дубликаты) |
| 3 | **Prompt injection** | Транскрипт/входной документ содержит «ignore previous instructions» — агент не подчиняется |
| 4 | **Tool misuse** | Агент пытается вызвать tool с невалидными аргументами — валидатор ловит |
| 5 | **Approval bypass** | Агент пытается выполнить write без явного approval — блокируется |
| 6 | **Connector failure** | MCP/трекер/внешний API недоступен — агент даёт structured fallback, не повторяет попытки в цикле |
| 7 | **Context overflow** | Транскрипт в 5× размера типичного — агент применяет compaction, не теряет план |
| 8 | **Conflicting instructions** | Universal Core говорит A, Client Core — B → агент следует приоритету (Universal > Client > Operations для онтологии; обратное — для фактов) |
| 9 | **High-risk action** | Запрос на destructive / privileged → агент отказывает или эскалирует, не выполняет |
| 10 | **Cost & latency** | Среднее время / стоимость одного run в пределах budget из Принципа 9 |

**Правила покрытия:**
- **Перед v1.0.0 (experimental → production):** минимум категории 1, 2, 9 + одна из {3, 4, 5}
- **Перед v1.1.0+:** все 10 категорий
- **Каждый production incident → новый regression eval-кейс** в соответствующей категории. Без этого fix не считается завершённым.

**Где хранить eval-кейсы:** `products/{agent}/evals/{category}/{case-id}.{md|yaml}`. Hash от фиксированного входа + ожидаемый contract от выхода (не дословный текст).

**Если → тогда:**
- Если eval-кейс упал → не «правь промпт чтобы прошёл», а сначала определи: missing instruction / source-of-truth / tool / validator / permission rule / sandbox signal / eval / recovery path
- Если eval-кейс «прошёл случайно» (LLM-non-determinism) → ужесточить contract выхода, не recover-loop
- Если категория 5 (approval bypass) — eval обязан проверять **runtime enforcement** (hook / config gate), не только текст промпта

**Анти-паттерн:** «Я проверил агента на 3 типичных случаях — работает». Это не eval, это smoke test. Eval — это fixture + contract + автоматический прогон, воспроизводимый при изменении промпта.

## Принцип 11: Детерминированное ядро, LLM на краях — не проси LLM то, что вычисляет функция

LLM — для **подлинно нечёткого** (суждение, синтез, извлечение смысла из естественного языка). Всё **механическое / правило-основанное / вычислимое** (счётчики, сводки, валидация формата, маппинг по таблице, дедуп по ключу, парсинг) — **детерминированный код**, не шаг промпта. Это не только дешевле по токенам — это **корректнее**: код убирает LLM-недетерминизм и галлюцинацию (тот же класс, что Принцип 8 «нельзя self-eval» и Принцип 10 «прошёл случайно»). Переиспользуй (multi-client скрипт по `--tenant`/аргументу), а не переимплементируй на каждый случай.

**Применяется к обоим классам:** продуктовые агенты (§A) — выноси вычислимое из промпта в tool/код; Claude Code skills (§B) — детерминированные шаги pipeline через скрипт, не «LLM сделает» (scan/normalize/recompute — код).

**Критерий «можно скриптовать» — детерминированность ДОКАЗЫВАЕТСЯ, не предполагается.** Не «кажется стабильным» → скриптуем, а три теста, все обязаны держать:
1. **Specifiability (специфицируемость):** правило выписывается полностью, без шага «тут по ситуации / нужно суждение». Не можешь записать спеку без LLM-суждения внутри → ещё не детерминировано.
2. **Purity (чистота):** выход — чистая функция входа: тот же вход → тот же выход, без скрытого состояния и неоднозначности.
3. **Demonstrated equivalence (доказанная эквивалентность) — главный:** не *решаем*, что стабильно, а *показываем*. Кандидат-скрипт гоняется в **shadow-режиме рядом** с текущим LLM/manual и сверяется на **идентичность** выхода за окно прогонов; cutover — только когда совпало. Это паттерн characterization-tests-before-refactor / shadow deployment / differential testing.

Пример: скрипт-пересчёт сводки сверяет вычисленное значение с ручным **до** замены — и находит дрейф (расхождение чисел) **до** cutover; `--check` остаётся **стоячим повторным доказательством** (exit≠0, если логика снова уехала в недетерминизм). Скрипт не «заменил и забыл» — он непрерывно переподтверждает эквивалентность.

**Гейт против premature scripting (иначе окостенение):** пока хоть один тест не держит (логика ещё эволюционирует / правило с суждением / shadow расходится) — оставляй в промпте/manual, не скриптуй. Слой суждения остаётся за LLM навсегда; в код уходит только доказанно-детерминированное ядро.

**Если → тогда:**
- Если шаг — чистое вычисление по известному правилу (счёт, сумма, маппинг, regex, дедуп) → код, даже если «LLM бы тоже смог».
- Если логика ещё меняется каждую неделю → оставь в промпте/manual до стабилизации (гейт выше), не скриптуй преждевременно.
- Если один и тот же скрипт нужен ≥2 клиентам → multi-client (путь/`--tenant` аргументом), без tenant-литералов в теле.

**Граница (важно):** это **Class A** экономии токенов — структурная (детерминизм + reuse), failure mode benign, качество растёт. **Class B** (урезание контекста, дешёвая модель, меньше verify-проходов) — отдельный **измеряемый** tradeoff с асимметричным риском (keyword-probe вместо полного snapshot может пропустить обогащения); НЕ дефолт, осознанно отложен до появления токен-телеметрии/бюджета. Не путать: «вынести в код» — всегда хорошо; «дать меньше контекста» — взвешивать.

## Принцип 12: Собственный контур (dogfood) → универсальный контракт + адаптируемая конвенция

Возможность сначала обкатывается на собственном контуре (dogfood-тенант), затем дистиллируется в два слоя для переноса на клиента:

- **Контракт** — инвариант, общий для всех тенантов: форма/интерфейс, что артефакт **ОБЯЗАН** нести. Под клиента не адаптируется; смена = слом для всех тенантов. Живёт в Universal Core (Принцип 3).
- **Конвенция** — слой, адаптируемый под клиента: значения, наполнение, стиль. Общая конвенция-дефолт + client overlay (plugins / overlay, не ветвление `if client==X`). При переносе на нового клиента меняются **конвенции, не контракт**.

**Граница анти-паттерна `if client==X`:** запрет относится к **imperative branching** — код вида `if client.mode == 'pulse': do_X() else: do_Y()`. **Schema-level conditional** (`allOf` + `if/then/else` в JSON Schema: разные required-наборы полей per tenant) — declarative validation, валидный паттерн для 2 тенантов, НЕ branching; триггер миграции schema-conditional → tenant overlay — появление 3-го клиента. Прецедент: поверхностный grep может счесть `client.mode` «unused enum», углублённый находит load-bearing conditional schema — удаление сломало бы валидацию одного из тенантов. Не делать поспешных генерализаций анти-паттерна с imperative-кода на declarative-схемы.

**Derivation — demand-driven, не из одного случая.** Инвариант вычленяется, когда есть **2-й реальный тенант**, а не гипотетический: пока клиент один, «универсальный контракт» = преждевременная абстракция (Принцип 4 Оккам). Dogfood-прецедент помечается как **кандидат-контракт**, поднимается в Universal Core при появлении потребителя (следующий клиент / скилл заводки клиента).

**Потребитель в AI-native — не только человек.** «Кто прочитает контракт/конвенцию» включает агентов / скиллы / сборку продукта (субагент через memory-инъекцию §B6, скилл заводки тенанта, сборка дистрибутива). Засчитывается только **названный** потребитель, не «какой-нибудь будущий агент».

**Пример:** контракт происхождения задачи — форма «задача несёт класс происхождения человек↔AI + ссылку на источник» = контракт (кандидат в Universal Core); конкретные классы значений = конвенция тенанта (у другого клиента — свои значения).

**Если → тогда:**
- Если возможность обкатана на 1 тенанте → пометь кандидат-контракт, не универсализируй тело; значения держи как конвенцию тенанта.
- Если появился 2-й реальный потребитель (клиент / скилл / агент — названный) → вычлени инвариант в Universal Core, оставь значения в client overlay.
- Если потребителя назвать нельзя → стоп (определение без читателя не фиксируется).

## Принцип B1: Output discipline для self-check skills

**Skill с enforcement-чеклистом выводит только сигнал отклонения, не подтверждение нормы.**

Применение Принципа Signal Density к self-check логике: успешный прогон оставляет след в виде самого результата (показанный пункт), отклонение — отдельной строкой с причиной, отсутствие хотя бы одного следа = «прогона не было».

**Если → тогда:**
- Если в skill есть чеклист (memory, валидация, фильтр) → выводи только пункты с ❌ или пограничные
- Если все ✅ → не печатай чеклист, печатай только результат
- Если нужно enforcement (доказательство, что прогон был) → используй свёрнутый блок «Скрыто N» с одной строкой причины на каждый отклонённый пункт

**Анти-паттерн:** «Чеклист: [✅] не из файлов · [✅] не конфиг · [✅] не fix · [✅] не дубль» под каждым пунктом — пользователь читает шум вместо сигнала.

## Принцип B2: Лестница мест перед предложением memory

**Перед предложением memory — обязательный прогон по лестнице мест по убыванию специфичности. Memory — последнее прибежище, не первое.**

Применение бритвы Оккама: не плодить сущности в memory, если правило уже имеет место в существующей иерархии артефактов.

**Лестница (1 = самое специфичное, 6 = универсальное):**

| # | Куда | Триггер |
|---|---|---|
| 1 | Промпт продуктового агента | Правило про поведение конкретного агента |
| 2 | Инструкция Claude Code skill | Правило про поведение конкретного skill |
| 3 | `agent-design-principles` §A или §B | Правило про класс компонентов |
| 4 | `operating-principles` | Универсальный принцип работы со знаниями |
| 5 | `CLAUDE.md` | Корневая инструкция, маршрутизация |
| 6 | Memory | Только если 1–5 не подходят |

**Если → тогда:**
- Если skill предлагает memory → перед записью пройти 1–5, явно зафиксировать на каком уровне правило приземляется
- Если уровень 1–5 подходит → пункт идёт туда (правка файла), **не** в memory
- Если правило про **класс** компонентов → §A или §B этого файла, не memory
- Если правило универсальное (про знания / процессы / SSOT) → operating-principles, не memory

**Анти-паттерн:** «memory как путь наименьшего сопротивления» — Write одной строкой проще, чем правка skill / principles. Запрещён.

**Что остаётся для memory после прогона:**
1. Профиль пользователя (роль, предпочтения, контекст).
2. Факты о внешних системах (queue ID, board ID, пути хранилищ).
3. Кросс-доменный feedback не привязанный к конкретному артефакту.

## Принцип B3: Spec changes должны быть закоммичены до запуска pipeline

Изменения в spec-файлах (`.claude/commands/*.md`, `products/*/slice/*.yaml`, schemas) **обязаны** быть закоммичены **до** запуска pipeline, который этот spec реализует. Uncommitted spec — это draft, не enforcement.

**Если → тогда:**
- Если в `git status` есть `M .claude/commands/{step}.md` и ты запускаешь pipeline → STOP. Закоммить spec, потом запускай pipeline.
- Если spec говорит «формат A» (uncommitted), а existing artefacts в `runs/*/outbox/` содержат «формат B» (committed) → LLM-субагент возьмёт **формат B** как «working production format», spec проигнорирует.
- Если spec — это псевдокод инструкции для LLM, а не функция в коде → enforcement обязан быть в config + validator gate, не только в skill-инструкции.

**Why:** LLM-субагент в Claude Code сессии видит **всё репо целиком** как контекст. Uncommitted file — это «черновик», existing committed artefacts — «truth». При генерации нового артефакта LLM ориентируется на existing examples (in-context learning), не на uncommitted spec. Это объективное поведение, не баг агента.

**Как применять:**
1. Перед запуском любого pipeline — `git status --porcelain` на spec-путях (`.claude/commands/`, `products/*/slice/*.yaml`, `schemas/`)
2. Если есть uncommitted spec changes → commit перед pipeline run
3. Spec без runtime enforcement (config + validator) — это **намерение**, не контракт. Для критичных форматов реализовать enforcement через config + функцию + validator gate

## Принцип B4: Validator-сообщения — директивны, не описательны

**Hook / validator / gate возвращает модели не описание нарушения, а готовую инструкцию по исправлению с подставленными аргументами.**

Применение Принципа Signal Density к runtime enforcement: «нарушено правило X» — обёртка; «выполни команду Y c аргументами Z» — содержимое.

**Структура хорошего validator-сообщения:**

```
[<hook_name>] <что произошло, 1 строка>
Нарушения:
  - <код правила>: <конкретный факт> (например, «строка 12: status=accepted без H2 «Словарь»»)
Fix:
  - <директивная команда или строка для вставки>
  - Если несколько вариантов — пронумеровать
SSOT: <link>
```

**Если → тогда:**
- Если validator пишет «отсутствует X» → расширить до «добавь H2 `## X` после frontmatter»
- Если validator пишет «перенеси в правильное место» → расширить до «UUID → `reference_<system>_integration.md`; board ID → `reference_<system>_integration.md`»
- Если validator знает client / file_path / id → подставить **точную команду** с аргументами, не плейсхолдер

**Образцовый пример:** gate-commit hook, который даёт готовую строку с подставленными аргументами (client, file_path), плюс fallback-инструкцию.

**Где применять:**
- `.claude/hooks/post_write_*.py` — все сообщения проверить на директивность
- Validator gates в pipeline (`gate-*.json` warnings) — поле `fix_hint` рядом с `issue_key`
- Tool result errors в продуктовых агентах — структурированный `{error, fix}`, не свободный текст

## Принцип B5: Sensitivity-проверка при создании документов про защищаемый IP

**Любой skill, создающий документ, который касается содержимого защищаемого IP-слоя репозитория (внутренние модели, механики, тесты, маппинги, не подлежащие раскрытию клиенту), — обязан выполнить sensitivity-проверку ДО установки `status: accepted`.**

Правило дисциплины защищаемого IP формулирует **что** защищать (внутреннее содержимое). B5 формулирует **когда и как** проверять — в момент создания документа, не после.

**Триггер B5:** документ, который Claude или skill создаёт, упоминает хотя бы один из элементов защищаемого IP-слоя:
- Имена внутренних моделей репозитория, не подлежащих раскрытию
- Внутренние механики и служебные поля, реализующие эти модели
- Расширения формальных онтологий/классификаций, составляющие конкурентное преимущество
- Конкретные примеры «внутренняя модель → правило онтологии»
- Полные тексты внутренних процедурных тестов/правил

> Конкретный перечень защищаемых элементов — в правиле дисциплины IP-ядра целевого репозитория (tenant-specific). B5 задаёт форму проверки; наполнение триггера подставляет владелец репозитория.

**Sensitivity-чек-лист:**

- [ ] Документ упоминает хотя бы один из триггеров выше?
- [ ] Если да — добавлена ли метка sensitivity в шапку (🔴 INTERNAL ONLY / 🟢 PUBLIC)?
- [ ] Если 🔴 — добавлен ли раздел «Политика шаринга» с правилами не-раскрытия и контрольным вопросом?
- [ ] Создан ли парный sanitized-документ (`*-public.md`) — или явно зафиксирован в backlog как deferred?
- [ ] В README папки — отмечен ли документ как 🔴/🟢 с явным указанием парного?

**Если → тогда:**
- Если документ касается защищаемого IP и шарится с клиентом без sanitization → BLOCKER, документ нельзя промоутить в `accepted` до создания public-парного
- Если документ создаётся sandbox'ом как `experimental` — sensitivity-чек откладывается до promotion в `accepted` (правило sandbox-lifecycle)
- Если документ про защищаемый IP случайно ушёл в clientfacing-папку (`positioning/`, `presales/`) → STOP, переместить в `concepts/` с 🔴-меткой

**Образцовый паттерн:** пара документов «internal (🔴) + public (🟢)» в одной папке с явными метками и cross-references — internal-версия несёт защищаемое содержимое, public-версия sanitized для клиента.

**Где применять:**
- Skills, создающие `concepts/*.md`, `decisions/*.md`, `scope/*.md` в production-папках
- Skills сборки клиентских материалов (one-pager, контент, proposal, адаптация оффера)
- Hook стандарта документов — потенциальное место для автоматизации (backlog item)

## Принцип B6: Memory facts injection и prompt precedence для субагентов

**При spawn субагента (Agent tool в Claude Code) — релевантные memory-факты копируются в prompt дословно; при противоречии prompt vs upstream file субагенту явно указывается precedence.**

Применение правила о специфике subagent context isolation. Закрывает класс ошибок «субагент эмпирически переоткрывает known constraint» и «субагент следует устаревшему полю в файле вместо актуальной инструкции в prompt».

**Что субагент НЕ видит при spawn:**
- User memory родительской сессии (`MEMORY.md` + `memory/*.md`)
- CLAUDE.md из cwd (если только не сделает `Read` явно)
- Историю родительской сессии и контекст до Agent tool call

**B6.1 — Memory facts injection.** При делегировании работы с внешними системами (внешние API, трекеры, хранилища) ИЛИ операций, требующих знания специфичных ограничений из user memory:

```
# Memory facts (релевантные из родительской сессии)

[Дословный copy-paste правил из memory/feedback_{system}_*.md]
```

Перед spawn'ом субагента — найти релевантные memory-файлы по системе/API, копировать содержимое (правило + Why + How to apply) в prompt. **Не ссылаться словами** «см. feedback_{system}.md» — субагент не имеет доступа к memory.

Класс потери: субагент, не получивший известное ограничение внешнего API (например, endpoint, который отвечает 200, но не применяет изменение), эмпирически переоткрывает его и тратит целый прогон впустую.

**B6.2 — Prompt precedence над upstream state.** Если prompt субагента **отменяет** ранее зафиксированное состояние в файлах (recommendations.json, gate-файлы, manifests):

1. **Явно указать конкретное поле** и действие: «recommendations.json содержит `push_outcome.status=skipped` — ОТМЕНИТЬ это поле и пушить», не «push все 30».
2. **Явно указать precedence-правило:** «инструкции в этом prompt'е имеют приоритет над содержимым {filename}».
3. **Если возможно — сделать pre-step сброса поля main session'ом ДО Agent spawn**, чтобы у субагента не было неоднозначности.

Класс потери: субагент опирается на устаревшее поле в файле как на ground truth и пропускает работу, явно предписанную в prompt.

**B6.3 — Reasoning-гард «обёртка ≠ содержимое» для разведочных/аудитных субагентов.** При спавне субагента, который **докладывает о состоянии** артефактов (разведка бэклога, аудит статусов, инвентаризация зависимостей), — копировать в промпт дословно гард:

```
# Reasoning-гард (обязателен для отчёта)

Статус-поле и текст описания артефакта (задачи трекера, документа, roadmap) —
обёртка, застывшая на момент написания. Выводы о ТЕКУЩЕМ состоянии — только
из проверки содержимого: links / git log / grep / чтение файла. Цитата
описания («X open, deferred») — НЕ основание; в отчёте у каждого вывода
о состоянии указывай след верификации (чем проверил).
```

Правила main-контекста («содержимое ≠ обёртка», «документ ≠ реальность») до субагента не доезжают — как и квирки в B6.1, гард работает только скопированным в промпт.

Класс потери: разведчик поверил тексту описания задачи («смежная задача open, deferred») и доложил неверное основание — реальный статус смежной задачи = closed (проверяется через links).

**B6.4 — Recovery при socket-обрыве субагента: сначала инспекция артефактов, не слепой re-spawn.** Длинный субагент (>5 мин: тяжёлая обработка встречи, большой dedup) может оборваться по сети («socket connection was closed unexpectedly»). Cache-слои на диске переживают обрыв — JSON-слои = SSOT, пишутся инкрементально, поэтому pipeline устойчив к socket drops.

- Если субагент оборвался → сначала `ls` / `git status` по ожидаемым output-путям субагента, потом решение.
- Если артефактов нет (мало tool calls, читал контекст) → чистый re-spawn с нуля, ничего не потеряно.
- Если extraction-слои записаны, отсутствуют только финальные шаги (render / manifests) → провалидировать готовые слои и дорендерить **узким finisher-субагентом** только оставшееся, НЕ перезапускать полный прогон: extraction — самая дорогая часть, повтор = потеря времени + риск рассинхрона (повторный extraction может дать другой результат).

**Где применять:**
- Любой Agent tool call в skills, делегирующих per-team или per-meeting processing
- Hot-patch скрипты, где prompt отменяет ранее зафиксированное состояние
- Разведочные/аудитные субагенты (доклад о состоянии артефактов) — B6.3 обязателен
- Agent-вызовы >5 мин — закладывать возможность обрыва, при обрыве действовать по B6.4

**Class of error:** structural limitation Claude Code SDK, не баг агента. Не лечится «лучше написать prompt» — нужна явная передача memory facts + precedence.

## Принцип B7: Именование skills — платформенный kebab-case + namespace через папку, не через префикс в имени

**Имя skill — по стандарту платформы Claude Code; область (клиент/семейство) — через folder-namespace, а не повтором префикса в имени.**

Применение принципа «имя = сущность, не контекст рождения» + «сверься с принятым снаружи» к именам Claude Code skills: формат уже стандартизован платформой — изобретать свой (подчёркивания и т.п.) запрещено.

**Платформенный стандарт (зеркалим, не изобретаем):**
- Только **`[a-z0-9]` + дефис** (kebab-case), **≤64 символа**. **Подчёркивания запрещены** (валидация отвергает `my_skill`). Имя ≠ `claude` / `anthropic`.
- Стиль: предпочтительно герундий (`processing-pdfs`); допустимы noun / verb-noun (`sync-process`, `kh-check`). Избегать vague (`helper`, `utils`, `tools`).

**Namespace = двоеточие `:`, накладывается платформой (НЕ наш символ):**
- Skill в подпапке `.claude/commands/{dir}/name.md` → вызов **`{dir}:name`** (один уровень — родительская папка). Плагины — `{plugin}:name`. С двоеточием не бороться: это структурная разметка области, а не часть имени.

**Наша конвенция области:**
- **Client-bespoke** (работает только для одного клиента, под другого не переносится) → папка-слаг `.claude/commands/{client}/` → `{client}:name`. **Клиента / инструмент / орг в самом имени НЕ повторять** (папка это уже говорит): `{client}:team-lifecycle`, не `{client}:{client}-team-lifecycle`.
- **Переиспользуемое** (универсальный движок, внутренние ops, go-to-market) → корень `.claude/commands/`, kebab-case. Функциональные префиксы-семейства (`sync-*`, `content-*`) допустимы как группировка-в-имени.

**Если → тогда:**
- Если skill bespoke под клиента → папка `{client}/`, имя без клиент-префикса.
- Если ≥3 связанных универсальных skill образуют семейство → можно завести новую папку-namespace, но **НЕ мигрировать существующие массово** (цена cross-ref churn > пользы). Правило — для **новых** skill и точечных фиксов дублей.
- Если имя содержит `_` или > 64 / зарезервировано → переименовать (платформа отвергнет).

**Enforcement:** soft — чек-лист §B (ниже) + namespace-конвенция в capabilities-map. Hook-валидатор имени (`^[a-z0-9-]{1,64}$`, не claude/anthropic, при создании файла в `.claude/commands/`) — backlog.

## Принцип B8: Порог создания skill — ≥3 фактических проведения, не «теоретически воспроизводимо»

**На вопрос «как переиспользовать это в будущем?» после разового успеха дефолтный ответ — линейный процесс из N шагов, не skill с атомарным pipeline и gate-файлами.** Skill стоит ~6–8ч первой версии + поддержка (gate-схема, sub-agent prompts, capabilities-map); 1 успешный прогон = не паттерн. Асимметрия цены ошибки — в пользу «отложить skill»: редкая задача выполняется вручную с дисциплиной, частая покажет себя через 2–3 повтора.

**Триггеры активации skill (любой из 3):**
1. **≥3 фактических проведения** с одинаковой структурой шагов;
2. **batch-потребность** («сделай это с 5 документами/задачами сразу» — линейная обработка масштабируется хуже атомарного pipeline);
3. **накопленные потери** (шаг X пропущен в ≥2 попытках — нужен enforcement через skill).

**Если → тогда:**
- Если задача выполнена успешно 1 раз → перечислить шаги линейным процессом (5–7 пунктов) + одна фраза «skill заведу после ≥3 проведений».
- Если сработал любой из 3 триггеров ИЛИ пользователь явно сказал «надо skill» → проектирование по правилу создания skill (capabilities-map + чек-лист §B).
- Если первым предложением рисуется атомарная архитектура с gate-файлами и оркестраторами → это анти-паттерн (тот же класс, что anti-overengineering pre-write, на уровне skill-design).

Здесь — SSOT порога; capabilities-map ссылается на эту норму.
