# Модуль компании

Модуль дополняет базового помощника и не отменяет его ограничения.
Компания хранит одну действующую редакцию в собственном Git-репозитории.
Проект подключает её явно; отдельное закрепление версии проекта не требуется.
Правила конкретной работы остаются в проекте. Общее для проектов поднимается
в компанию, общее для компаний — в помощника после проверки применимости.
При переносе исходное место ссылается на новый источник вместо копирования.

## Состав и подключение

Модуль — папка `ivan-module/` в репозитории компании:

```text
ivan-module/
├── module.json
├── rules.md
├── _ivan_company.py
├── ci.yml
└── README.md
```

Первые два файла — настройки и инструкции. Программа `_ivan_company.py`
совпадает с общей программой проверки из поставки помощника; её копия нужна
серверу без установленного плагина. Правки программы приходят из обновления
помощника, а не вносятся отдельно в компании.

Пример `module.json`:

```json
{
  "schema_version": 1,
  "name": "Company",
  "version": "1.0.0",
  "rules": "rules.md",
  "documents": {"roots": ["docs"], "exclude": [], "warn_file_count": 10}
}
```

После получения репозитория компании подключить его из проекта:

```sh
python3 /path/to/ivan/hooks/_ivan_company.py install \
  --source /path/to/company/ivan-module --target /path/to/project
```

Команда создаёт `.ivan/project.json` с относительным путём к общей локальной
копии. Добавьте этот файл в Git. Для одинаковой структуры рабочих папок он
работает у всех участников; при другом расположении можно задать локальную
переменную `IVAN_COMPANY_MODULE`. Она также используется в CI.
Без явного подключения проверка не действует. Неисправный подключённый модуль
даёт ошибку, а не успешную проверку. В среде с `.es-connection.json` модуль
не применяется: порядок этой среды сохраняется.

## Что проверяется

Обязательные требования внутри выбранных папок:

- папка с документами имеет `README.md`;
- README содержит строку «Назначение папки:» и ссылки на документы;
- локальные ссылки ведут на существующие файлы и Markdown/HTML-якоря.

Учитываются Markdown, PDF, Word, Excel, PowerPoint и HTML. Проверка ссылок
внутри бинарных форматов не выполняется. Сетевые ссылки не запрашиваются.
Порог числа документов — предупреждение, не запрет; большая однородная папка
может оставаться целой. Новая подпапка с одним-двумя документами вызывает
предупреждение при сравнении с базовым коммитом.

Проверка не определяет соответствие документа теме, полноту содержания,
допустимость доступа или смысловое противоречие базовым правилам. Это
проверяет автор. Неизвестные машинные параметры отклоняются; отключения
обязательных проверок в схеме нет.

## Локально и на сервере

Хук после записи проверяет затронутую папку; при изменении README — её индекс.
Хук старта читает только локальные инструкции, не загружает и не исполняет
код из репозитория компании. Записи командой, другой редактор и отключённый
плагин могут пройти мимо локального хука.

Общий контроль выполняется командой:

```sh
python3 /path/to/company/ivan-module/_ivan_company.py check --root .
```

Сервер запускает эту же программу для всей подключённой области. Код выхода
`0` — ошибок нет, `1` — нарушены требования, `2` — проверка не выполнена.
Предупреждения не меняют успешный код. `--base <commit>` дополнительно
позволяет определить новые маленькие папки.

Серверный шаблон подключается через `include` в конфигурации CI проекта.
Он получает действующую редакцию компании и печатает её commit SHA. Доступ
CI к закрытому репозиторию компании и доступность runner проверяются отдельно.
Для обязательности нужно запретить слияние при неуспешной проверке; локальные
Git-хуки через `git pull` автоматически не устанавливаются.

## Поддержание

Обновление компании приходит через `git pull` её репозитория, обновление
механизма — через обновление помощника и синхронизацию программы в модуле.
Программа не обновляет себя автоматически. Периодическая сверка — при
недельном разборе проекта. Сигнал сбоя — документ принят на сервере при
неуспешной либо незапущенной обязательной проверке.
