# Workflow: Стандарты написания документов

| Параметр | Значение |
|----------|----------|
| Статус | ✅ Active |
| Обновлён | 2026-08-31 |
| Назначение | Стандарт оформления decisions / scope / spec / concept перед статусом `accepted` или `ready`: правила структуры (П1–П13), языковые критерии (Я1–Я9), двухпроходный режим, чек-лист. Применяется при создании или промоушене документа в production. |

> **Зачем документ.** Автор пишет заметку себе — плотно, своей терминологией, с опущенными звеньями, которые держит в голове. Читателю через полгода (и любому другому человеку) этих звеньев не хватает, а автор их дефицита не видит: для него текст полон. Здесь собрано, что именно достраивается при переходе от заметки к передаваемому материалу, — набор проверяемых правил вместо «написать понятно», которое не операционализируется и потому не исполняется.

## Аудитория документов

Документы должны быть понятны:

1. **Члену команды**, который не думает в тех же терминах, что автор
2. **Новому человеку** при онбординге в проект
3. **Внешнему ревьюеру**, не знакомому с историей решений
4. **Самому автору** через 6 месяцев

## Скоуп применения

Полный набор правил применяется к документам:
- со статусом `accepted` или `ready`, **и**
- типа decision / scope / spec / concept, **и**
- длиннее 150 строк **или** предназначенным для внешнего ревью

**Облегчённый набор** (только П1–П5 + П10 + П12, Я1–Я8) — для коротких ADR (≤150 строк), черновиков, экспериментальных spec'ов в `_sandbox/`. П10 универсален — применяется и в коротких документах.

**Не применяется** к: операционным трекерам, выжимкам встреч, memory-файлам, README в папках, гайдам типа этого.

## Формат шапки метаданных (применяется ко ВСЕМ новым .md)

Перед Write нового .md — явно выбрать **ровно один** формат шапки по типу файла:

| Тип файла | Формат шапки | Пример пути |
|-----------|--------------|-------------|
| Skills | YAML frontmatter (`---...---`) | `.claude/commands/*.md` |
| Операционные / стратегические / методология | Таблица `\| Параметр \| Значение \|` после H1 | документы проекта и методологии |
| Выжимки встреч | Blockquote `>` (исключение) | `*/meetings/` |

**Запрещена двойная шапка** — YAML frontmatter + таблица с теми же полями в одном файле. Если оба уже написаны — удалить YAML, оставить таблицу (для не-skill файлов). Причина класса ошибки: оба шаблона подтягиваются «на всякий случай» при быстром Write без явного выбора формата. Enforcement — инкрементальная валидация изменённых .md (проверка формата шапки).

## Режим работы: два прохода

Не пытайся писать сразу «онбординг-готово» — это убивает плотность мысли и скорость автора.

**Проход 1 — черновик.** Автор (и Claude от его лица) пишет в естественном стиле, плотно, с собственной терминологией. Цель — зафиксировать мысль.

**Проход 2 — редактура.** Прогон по правилам. Claude предъявляет автору **список конкретных нарушений**. Только после согласования — переписывает.

Документ не считается готовым к промоушену в `accepted` без явного прохода 2.

## Правила структуры (П1–П13)

### П1. Словарь в начале документа

Перед основным текстом — секция «Словарь». В неё попадает любая сущность, которая:
- упоминается в документе больше двух раз, **и**
- не является общеизвестной для целевой аудитории

**Формат строки:**
**Термин** — что это в реализационных терминах (агент / схема / файл / процесс / роль) — зачем нужно.

**Пример:**
- **Project-analyst** — LLM-агент с системным промптом, запускаемый раз в неделю на команду — формирует рекомендации по фокусу.
- **Producer Contract** — JSON-схема и правила её заполнения — единый формат для всех источников рекомендаций.

### П2. Расшифровка префиксов и кодов при первом упоминании

При первом появлении в документе:
- **L-arch** → L-arch (Layered architecture, слой архитектурных инвариантов)
- **Inv-1** → Inv-1 (Invariant 1, первый инвариант)
- **T1.1** → T1.1 (Task 1.1, первая задача фазы 1)

Все внутренние коды, префиксы, сокращения раскрываются один раз. Дальше можно использовать сокращение.

### П3. Каждая внешняя ссылка — с одной строкой контекста

При упоминании внешнего идентификатора (номер цели, ID задачи, имя другого документа) — одно предложение о содержании прямо в тексте.

**Плохо:** «Цель C-251 переформулируется как Matching engine LLM-агент».

**Хорошо:** «Цель C-251 (текущее название: Duplicate detector — детерминированный скрипт обнаружения дублей) переформулируется как Matching engine — LLM-агент с измеримой точностью».

Документ должен читаться без открытого трекера.

### П4. Сущность вводится через «что это», потом через «что делает»

Первое предложение про любую сущность отвечает на вопрос **«это какого типа объект в системе»**, и только потом — что эта сущность делает.

**Плохо:** «Project-analyst анализирует портфель задач и производит рекомендации».

**Хорошо:** «Project-analyst — это LLM-агент с системным промптом, запускаемый раз в неделю по расписанию. Он анализирует портфель задач и производит рекомендации».

### П5. Разные слои сущностей маркируются явно

В тексте смешиваются сущности минимум пяти типов:

1. **Физические инструменты** — Claude Code, cron, launchd, внешний трекер задач
2. **Логические концепты** — Producer Contract, Matching engine, Augmentation pattern
3. **Форматы данных** — JSON Schemas, manifest.yaml
4. **Процессные артефакты** — pipeline-issues.md, runbook, gate-файлы
5. **Организационные понятия** — фаза, acceptance, доп.соглашение

Когда они встречаются в одном предложении, тип каждой должен быть прозрачен.

**Плохо:** «Matching engine — центральная компонента augmentation pattern».

**Хорошо:** «Matching engine (LLM-агент) — центральная компонента подхода augmentation (методологическая концепция, описанная в Inv-4)».

### П6. Раздел «Для кого этот документ»

*(Только для документов из полного скоупа, см. раздел «Скоуп применения».)*

Первая секция после заголовка — три-четыре строки:

- **Кому адресован** документ
- **Что нужно знать заранее** (3–5 пунктов с ссылками на предварительные документы)
- **Что читатель сможет сделать** после прочтения

### П7. Карта документа после словаря

*(Только для документов длиннее 500 строк.)*

Одна страница: какие разделы в документе, что в каждом, в каком порядке читать. Две колонки: «первое чтение» (обязательно) и «глубокое чтение» (детали).

### П8. Раздел «История и контекст»

*(Только для decisions и scope-документов в полном скоупе.)*

Одна страница в начале:

- Что было раньше (предыдущее решение / отсутствие решения)
- Какие были варианты
- Почему выбрали именно этот
- Какие наблюдения или триггеры привели к решению

### П9. Раздел «Если бы я объяснял устно»

*(Только для документов длиннее 500 строк или scope/concept в полном скоупе.)*

В конце документа — упрощённая, осознанно избыточная версия на 1–2 страницы. Не вместо документа, а в дополнение. Место, куда читатель может приземлиться, если запутался выше.

### П10. Документ фиксирует результат, не процесс его выработки

В kernel-документах (онтология, decisions, principles, concepts со статусом `accepted` или `ready`) фиксируется **что есть в системе**, не **как мы к этому пришли**. История выработки знания живёт в **session-notes**, **git log**, **open-questions** — не в самом документе.

**Что НЕ писать:**

- Update-ремарки про отвергнутые формулировки («гипотеза X была, но отвергнута через критический разбор по N причинам...»)
- Секции «Что НЕ X» / «Что отвергнуто» / «Антипаттерны прошлой версии»
- Перечисление противоречий, заставивших отказаться от предыдущей версии
- «На момент написания предполагалось Y, но позднее...»
- «Сессия началась как fix Z, через N итераций обнаружила...»
- Ссылки «полный материал — в session-notes», встроенные в основной текст (не в раздел «История и контекст» П8)

**Что писать:**

- Факт: «X откачен как ошибочный. Причина: K тавтология, A не флаг типа»
- Указатель на actual место текущего знания: «Operational правила — в §X v4.1.2»
- Если контекст возникновения структурно важен (П8 «История и контекст») — кратко **что было раньше** и **триггер решения**, без перечисления отвергнутых промежуточных формулировок

**Когда отвергнутое знание уместно в документе:**

- В **changelog** документа — одна строка факта «X откачен» (без перечисления противоречий)
- В **session-notes** — полная история выработки (там она ценна как journal)
- В **git log** сообщении коммита — почему меняем
- В **open-questions** — только **актуальные** open questions, не закрытые отказом

**Тест перед Write:**

> «Если убрать этот блок, что читатель потеряет в понимании **текущего состояния**?»
> Если ответ «узнает историю, как мы к этому пришли» → блок не нужен в kernel.

**Класс ошибки, который П10 предотвращает:** «документировать процесс мышления вместо результата». Особенно опасно при двойной валидации (гипотеза → отказ → новая гипотеза → отказ → результат) — соблазн зафиксировать **путь** для будущих читателей. Этот путь живёт в session-notes и git log, не в kernel.

**Почему автор не вычищает это сам — и как вычистить надёжно (anchoring).** Минимализм автора **заякорен на рассуждении, через которое он только что прошёл**: для него каждый абзац «следа пути» обоснован — он помнит, зачем его написал. Поэтому собственная редактура П10 ненадёжна — автор не видит лишнего, потому что для него оно не лишнее. **Приём:** проход на сокращение делается в **свежем контексте** — отдельным агентом/сессией с единственной задачей «срежь всё, что обосновано путём автора, а не нуждой читателя в понимании текущего состояния». Это тот же принцип, что «агент не оценивает свой output»: **simplification, как и evaluation, не делается тем же контекстом, что генерировал.** Различать: critique говорит «вот слабое место», simplification — «вот это лишнее, режь»; это разные акты, второй проход П10 — про второе.

### П11. ADR/decision продуктового слоя — tenant-agnostic

Decision продуктового/переиспользуемого слоя фиксирует **агностичное** решение и **не содержит примеров клиентов**. Конкретный клиент, его артефакты, метрики, имена команд, названия его моделей — это **инстанциация**, она живёт отдельно (client-decisions, client-explorations), а ADR на неё **ссылается**.

**Что НЕ писать в продуктовом ADR:**
- имена/пути клиентских артефактов как несущие примеры (client-модель, client-доска, client-очередь), client-slug, имена команд клиента, конкретные метрические числа клиента;
- «например, для {клиента}: …» там, где пример **несёт** объяснение (если убрать — понятность теряется → пример стал носителем, это уже инстанциация).

**Что писать:** универсальные термины («доменная модель», а не имя файла client-модели; «юнит», а не имя команды; «операция консолидации», а не имя client-скилла). Client-инстанциация + доказательства на реальных данных → отдельный exploration/client-doc, ADR даёт на него пойнтер.

**Граница (не перерегулировать):** упоминание client-значения как **иллюстрации в комментарии/докстринге**, без несущей роли, допустимо (пример в докстринге ок, исполняемой привязки нет). Различие — **где живёт identifier/пример**: продуктовый слой (агностично) vs client-инстанс (конкретно). Тест: «если стереть client-имя, решение остаётся понятным?» → да = было иллюстрацией (ок); нет = было носителем (вынести в инстанциацию).

**Класс ошибки, который П11 предотвращает:** ADR продуктового слоя, написанный вокруг одного клиента, читается как client-специфика и не переносится на 2-го клиента; плюс client-контекст рождения «прилипает» к универсальному решению. Расширяет принцип «имя = сущность, не контекст рождения» и правило de-private кода — с **кода** на **decision-документы**.

**Enforcement:** soft (этот стандарт + Проход 2 при промоушене). Hook проверки стандарта оформления — расширить детектом client-литералов в `type: decision` вне client-путей.

### П12. Блок «Зачем документ» — в теле, не в шапке

*(Для смысловых типов: concept / analysis / model / план. Не применяется к операционным артефактам — трекеры, срезы, выжимки, отчёты по шаблону.)*

Сразу после таблицы метаданных, до первого раздела — блоквот:

```markdown
> **Зачем документ.** {чего не хватало без него; какую рамку он держит; что сломается, если его удалить}
```

**Что сюда пишется:** основание существования документа — почему знание оформлено отдельным файлом, а не абзацем в соседнем. Не пересказ содержания и не адресат.

**Три поля рядом и чем отличаются:**

| Поле | Отвечает на | Где живёт |
|------|-------------|-----------|
| `\| Назначение \|` в таблице | кому документ и что забирают | служебный слой (шапка) |
| «Зачем документ» (П12) | почему существует отдельно | тело документа |
| «Для кого этот документ» (П6) | адресат, предпосылки, что сможет сделать | тело, после П12 |

**Запрещено `## Назначение` первым разделом** — он повторяет карточку из шапки и занимает место, где должен стоять замысел. Поле в таблице остаётся, раздел-дубль удаляется.

**Почему блок в теле, а не поле в шапке — структурная причина.** Служебный блок метаданных вырезается при вёрстке в HTML: в документах, уходящих получателю, он и вовсе заранее прячется в HTML-комментарий, чтобы не доехать. Это правильное поведение — служебную карточку получателю показывать не надо. Следствие: всё, что должно пережить экспорт и дожить до читателя, обязано жить в теле. Класс ошибки: замысел, записанный полем шапки, исчезает из свёрстанного документа полностью — при том что «зачем эта штука» есть первое, что читает открывший.

**Два читателя, одно место.** Агенту блок даёт рамку при сборке, правке и поиске (что в документ не относится); человеку — ответ «почему это здесь лежит» при возврате к файлу через месяцы. Оба читают сверху, до содержания, — поэтому форма одна.

**Блок не заменяет вопрос до сборки.** Замысел, дописанный задним числом в отведённое место, экономит только чтение, не переделку. Ценность, которая замеряется, — у вопроса, заданного **до** работы: в разборе сборки регулярного отчёта из 84 минут потерь 65 снимались вопросами, заданными до начала. П12 фиксирует результат такого вопроса в тексте, сам вопрос — предмет процедуры сборки.

**Класс: культура.** Точка активации — `Write` документа смыслового типа; каденция — каждое создание и Проход 2 при промоушене; сигнал деградации — блок, пересказывающий содержание вместо основания, либо возврат `## Назначение` первым разделом. Хук не заводится: «несёт ли блок основание или пересказ» код не наблюдает.

**Скоуп применения к существующим документам:** правило действует на новые и на те, что проходят Проход 2. Разовый проход по корпусу не проводится — документы с дублирующим первым разделом переориентируются при следующей содержательной правке, не раньше.


### П13. Поле «Обновлён» держит одну запись, журнал живёт в теле

*(Применяется ко всем документам с таблицей метаданных.)*

В поле `| Обновлён |` — **текущая дата и одна строка сути** (что изменилось, ≤200 символов). Предыдущие записи переносятся в раздел `## История изменений` в конце документа:

```markdown
## История изменений

| Дата | Что изменилось |
|------|----------------|
| 2026-08-31 | Самая свежая запись сверху |
| 2026-08-21 | Предыдущая |
```

**Правило записи — REPLACE, не append.** Новая правка **заменяет** содержимое поля, прежнее уходит первой строкой в журнал. Цепочка «Ранее … Ранее … Ранее …» внутри ячейки запрещена.

**Класс ошибки, который П13 предотвращает.** Правка требует где-то отметиться; единственное поле про изменения — `Обновлён`; записи прирастают к нему. Каждая добавляет фразу и по отдельности не превышает порога заметности — а через десяток правок ячейка перестаёт читаться и шапка теряет функцию карточки. Это прирост без отведённого места для роста: правило требует зафиксировать изменение, но не называет куда, и всё стекает в ближайшее подходящее поле. Замер 2026-08-31: двенадцать документов с полем длиннее 400 символов, худшие — 27 327, 5 099, 4 308, 3 667 символов; в самом длинном шапка перестала быть шапкой.

**Почему журнал в теле, а не в шапке.** Шапка отвечает на вопрос «что это за файл» и читается перед решением, открывать ли его. История отвечает на «как он к этому пришёл» и нужна тому, кто уже внутри. Смешение стоит первому читателю всей карточки: чтобы дойти до следующего поля, надо проскроллить журнал.

**Граница.** Документ, у которого правок одна-две, журнала не заводит — поле с датой и строкой достаточно. Раздел появляется на третьей записи. Операционные артефакты с собственным журналом (`pipeline-issues`, `sync-changelog`, трекеры) уже устроены верно — П13 их не меняет.

**Прецедент механизма.** Правило не новое по сути: то же самое записано в процедуре экспорта трекеров — «ровно одна строка текущего прогона, REPLACE не append, прежнюю строку prepend в журнал». Там оно работает; П13 распространяет его с трекеров на документы.

**Класс: регламент (будильник).** Enforcement — проверка длины поля в хуке стандарта оформления: **warn**, не блок. Точка активации — `Write`/`Edit` документа с таблицей метаданных; каденция — каждая правка; сигнал деградации — жалобы на ложные срабатывания (→ правка порога) либо обходы предупреждения.

**Порог — 400 символов значения поля, и он не на глаз:** вычищенные документы дали 182–383, а всё длиннее в замере оказывалось склейкой из двух и более записей. Одной длины мало: 3061 символ в одном документе был семью осмысленными записями по версиям, а не небрежностью. Поэтому проверка требует **двух** признаков — длина выше порога **и** видимая склейка (вторая дата в значении либо слово «Ранее»). Почему warn, а не блок: отличить журнал от длинной честной записи код может лишь эвристикой, и она не настолько надёжна, чтобы останавливать работу.

## Языковые критерии (Я1–Я9)

### Я1. Тест на эквивалент

Перед использованием английского слова — задать вопрос: **«есть ли русское слово ровно с тем же значением в этом контексте?»** Если есть — использовать его.

**Типовые замены:**

| Англицизм | Замена |
|---|---|
| owner | ответственный |
| scope | рамки |
| input | основа / исходник |
| success | успех |
| baseline | точка отсчёта |
| track | направление |
| onboarding | ввод в работу |
| runbook | инструкция |
| gateway | точка входа |
| finalization | завершение |
| disclaimer | оговорка |
| timing | срок |
| edge cases | пограничные случаи |
| failure modes | сценарии отказа |
| sanity check | проверка состоятельности |
| dogfooding | использование на себе |
| customer-facing | обращённый к клиенту |
| out of scope | вне рамок |
| orphan | висячий объект |
| realization-cycle | цикл реализации |
| alignment | согласование |
| execution | исполнение |
| output | результат |
| actionable | требует действия |
| backup (роль) | дублёр |
| pending | в очереди / задерживается |
| recurring | повторяющийся |

Если эквивалента нет или он искажает смысл — англицизм остаётся, но проходит Я3.

### Я2. Запрет на гибриды через апостроф

**Запрещены** конструкции: producer'ом, tenant'а, recommendation'ов, pipeline'а, gate'ы, tracker'е, snapshot'а, LLM'ом.

Выбор **одной из двух систем** (одна на весь документ):

1. Слово остаётся английским и **не склоняется**: «работа producer», «через producer», «два producer».
2. Слово **транслитерируется** и склоняется по-русски: «продьюсера», «продьюсерами», «тенант», «тенанта».

**Особенно запрещены глагольные гибриды:**
- эмитит → испускает / производит / выдаёт
- augmenting'ует → дополняет
- промоушн в tracker → перенос в трекер / повышение в трекере

#### Исключение: формальные имена онтологических типов

Имена онтологических типов в схеме (формальные термины с CamelCase: Decision, Rule, Concept, IndicatorRelation, KeyChange, StrategyGoal и др.) — это **proper nouns**, формальные имена классов в онтологии. Для них апостроф при склонении **разрешён** в онтологических документах (glossary, ADR онтологического расширения, schema-описаниях): «<внутренняя причинная модель> Decision'а», «семантика Rule'ы», «extension Concept'а через framework_membership».

Обоснование исключения: эти термины не общая лексика, а формальные имена типов схемы. Транслитерация («Десижна» / «Рула» / «Концепта») разрушает связь с формальной онтологией; не-склонение («применительно к Decision») делает текст громоздким на 100+ случаях в одном glossary. Apostrophe-склонение — устоявшийся паттерн для онтологических документов.

**Скоуп исключения:**
- Документы с `type: decision` ИЛИ путём в онтологическом слое — apostrophe-гибриды разрешены **только** для CamelCase онтологических имён типов.
- Общие технические термины (producer, tenant, pipeline, gate, tracker, snapshot, LLM) — **остаются запрещены** даже в онтологических документах. Это не онтологические типы.

**Hook поведение:** `find_apostrophe_hybrids` пропускает CamelCase pattern (`[A-Z][a-z]+[A-Z]?...`) в документах с `type: decision` или в путях онтологического слоя. Pattern `[a-z][a-z_-]+['’][а-яё]+` (lowercase) проверяется всегда.

### Я3. Каждый оставленный англицизм определён в словаре

Если англицизм оставлен (по Я1 эквивалента нет), он **обязан** быть в словаре документа с одной строкой определения. Без исключений.

Pipeline, overlay, producer, tenant, matching engine, augmentation, hook, snapshot, gate, frontmatter — каждое требует строки в словаре.

**Исключения** — устоявшиеся технические термины, известные всем читателям: OKR, KR, MCP, JSON, YAML, API, URL.

### Я4. Запрет на цепочки английских слов

Больше двух английских слов подряд без русских связок — переписать.

**Плохо:** «equal-citizen producer contract recommendation pipeline».

**Хорошо:** «producer как равноправный источник, работающий по единому контракту в рамках pipeline».

### Я5. Запрет на маркетинговые кальки

| Калька | Замена |
|---|---|
| equal-citizen | равноправный |
| first-class | самостоятельный / полноценный |
| production-grade | промышленный |
| customer-facing | обращённый к клиенту |
| premature abstraction | преждевременная абстракция |
| proof of approach | подтверждение подхода |
| added value | дополнительная польза |
| actionable item | задача к выполнению |
| legitimate | допустимый / правомерный |
| cloud-readiness | готовность к облаку |
| read-before-write | чтение перед записью |

### Я6. Запрет на нерасшифрованные аббревиатуры

При первом упоминании любой аббревиатуры — расшифровка в скобках:

- **MVP** (Minimum Viable Product, минимально жизнеспособный продукт)
- **PII** (Personally Identifiable Information, персональные данные)
- **MCP** (Model Context Protocol)
- **KR** (Key Result, ключевой результат)
- **SLA** (Service Level Agreement, соглашение об уровне обслуживания)

**Исключение** — аббревиатуры, которые гарантированно знает каждый читатель (API, JSON, URL). При сомнении — расшифровывать.

### Я7. Запрет на внутренние коды без расшифровки

Дублирует П2 в языковом блоке: каждый внутренний код (L-arch, Inv-1, T1.1, Ev-1, Phase 1, Track X) раскрыт при первом упоминании.

### Я8. Тест на чтение вслух

Каждое предложение должно нормально читаться вслух по-русски. Если приходится переключать языковой регистр в середине фразы — переписать.

**Плохо:** «Pipeline не генерирует план команды, а augmenting'ует существующий портфель».

**Хорошо:** «Конвейер не создаёт план команды, а дополняет существующий портфель задач».

### Я9. Тест на онбординг

Финальный критерий. Перед публикацией: представить, что документ читает человек, который не работает в проекте.

На каких словах он остановится и пойдёт гуглить? Каждое такое слово — либо в словарь, либо заменить на русское.

## Чек-лист перед публикацией

Перед статусом `accepted` или `ready` — пройти по списку, **предъявить автору нарушения**, исправить после согласования.

**Структура (для полного скоупа):**

- [ ] Поле «Обновлён» — одна запись, прежние в `## История изменений` (П13)
- [ ] Есть блок «Зачем документ» после таблицы, `## Назначение` первым разделом нет (П12)
- [ ] Есть словарь в начале (П1)
- [ ] Все префиксы и коды раскрыты при первом упоминании (П2, Я7)
- [ ] Каждая внешняя ссылка с одной строкой контекста (П3)
- [ ] Каждая сущность определена через «что это» до «что делает» (П4)
- [ ] Слои сущностей маркированы (П5)
- [ ] Есть раздел «Для кого этот документ» (П6) — если применимо
- [ ] Есть карта документа (П7) — для документов >500 строк
- [ ] Есть раздел «История и контекст» (П8) — для decisions/scope
- [ ] Есть раздел «Если бы я объяснял устно» (П9) — для длинных scope/concept
- [ ] Нет Update-ремарок про отвергнутые формулировки, секций «Что НЕ X», перечислений противоречий промежуточных гипотез (П10)
- [ ] ADR продуктового слоя не содержит несущих примеров клиента (П11)

**Язык (применяется всегда):**

- [ ] Легко заменимые англицизмы заменены (Я1)
- [ ] Нет гибридов через апостроф (Я2)
- [ ] Каждый оставленный англицизм — в словаре (Я3)
- [ ] Нет цепочек больше двух английских слов (Я4)
- [ ] Маркетинговые кальки заменены (Я5)
- [ ] Все аббревиатуры расшифрованы при первом упоминании (Я6)
- [ ] Каждое предложение читается вслух (Я8)
- [ ] Пройден тест на онбординг (Я9)

## Как Claude применяет этот стандарт

**При создании нового документа** типа decision / scope / spec / concept в полном скоупе:

1. Сначала пишется черновик в естественном стиле автора (Проход 1).
2. Затем Claude **явно** проходит по правилам и формирует список нарушений в формате:
   ```
   П1 (словарь): отсутствует.
   П3 (контекст ссылок): C-251, C-258, C-469 — без пояснений.
   Я2 (гибриды): найдено 14 случаев: producer'ом (3×), tenant'а (5×), ...
   Я6 (аббревиатуры): MVP, PII, MCP, KR — без расшифровки.
   ```
3. Автор согласует, какие нарушения исправить (некоторые могут быть осознанным выбором).
4. Claude переписывает согласованные места.

**При промоушене документа из `_sandbox/` в production** (статус `experimental` → `accepted`) — обязательный прогон по чек-листу.

**При правке существующего документа** — сначала прогон по чек-листу, отчёт о состоянии, затем точечные правки.

## Что этот стандарт НЕ делает

- Не запрещает английские термины, ставшие частью технического языка (pipeline, overlay, schema). Запрещает использовать их **без определения**.
- Не требует «писать проще» — плотность мысли сохраняется. Требует **развёртывать систему обозначений** для читателя.
- Не отменяет авторский стиль. Работает на втором проходе, не на первом.
- Не применяется к коротким операционным документам и memory-файлам (см. «Скоуп применения»).
