# /close-session — Завершение рабочей сессии

Структурированное закрытие сессии. Три фазы: actionable extraction → самооценка качества → End of Day. Перед ними — Phase 0 (авто-закрытие задач трекера), если трекер подключён.

Skill следует operating-principles: Signal Density (вывод — только сигнал, не подтверждение нормы), Бритва Оккама (не плодить артефакты и фазы, если они растворяются в более общем механизме).

## Iron Law

**Спрашивай только там, где не уверен.** Подтверждение — управляющий сигнал, а не ритуал. Применение Принципа 3 (Signal Density) к диалогу: вопрос с очевидным ответом — шум.

- Уверен в пункте → выполнить молча, в конце доложить «сделано».
- Не уверен (пограничный, спорный, memory с риском дубля) → спросить через AskUserQuestion.
- Memory всегда требует подтверждения — это исключение по высокой цене ошибки.

## Трекер-интерфейс (контракт вариативности)

Phase 0 работает через **трекер-интерфейс** — 2 метода, реализацию которых даёт **экземпляр** (адаптер под конкретный трекер). База знает только контракт; конкретный трекер подключается адаптером экземпляра — база трекер-нейтральна и не несёт трекер по умолчанию.

**Разрешение конфига (в начале Phase 0):**

1. Найди инстанс-конфиг: единственный `*/.sync-config/sync-config.yaml` в репозитории, секция `tracker:`.
2. **Нет секции `tracker:`** (или файла нет) → **Phase 0 пропускается молча**. Трекер не подключён; у базы нет дефолтного трекера — это норма, не ошибка.
3. Есть → прочитай `tracker.type` и загрузи адаптер по `tracker.adapter_ref` (документ реализации в overlay экземпляра). Дальше все обращения к трекеру — только через 2 метода адаптера, напрямую к API трекера скилл не ходит.

**Метод 1 — `list_open(session_text) → [Task]`**
- Вход: текст сессии.
- Адаптер по своему `mention_pattern` извлекает id упомянутых задач, запрашивает их в трекере, возвращает только незакрытые (`open` / `in_progress`) как `Task{ id, summary, description, status }`.
- Двусмысленный id (например, голое число, которое может не быть task-id) → адаптер помечает `ambiguous: true` → задача идёт в ветку **ASK**, не CLOSE.

**Метод 2 — `close_task(id, reason, comment) → Result`**
- Адаптер переводит задачу в завершённое состояние средствами своего трекера и прикрепляет `comment` (список хешей коммитов сессии).
- `reason` — семантика закрытия из закрытого словаря интерфейса: `done` (выполнено коммитами) / `duplicate` (дубль другой задачи). Маппинг на механику трекера — забота адаптера (в одном трекере это резолюция, в другом — перенос карточки в колонку).
- Если трекер **не поддерживает** прикрепление комментария (ограничение API) → адаптер возвращает `comment_persisted: false`. Тогда commit-hash-запись **не теряется**: отражается в финальной сводке сессии.

**Инвариант:** скилл оперирует только этими двумя методами и словарём `reason`. Всё трекер-специфичное (формат id, done-механика, ограничения API, где брать статус) — внутри адаптера.

## Phase 0: Авто-закрытие задач трекера

Если трекер подключён (см. выше) — до Actionable Extraction пройти по всем задачам, упомянутым в сессии, и решить судьбу каждой на основе коммитов. Не спрашивать там, где сверка с коммитом даёт однозначный ответ.

### Шаги

1. **Собрать кандидатов.** Вызови `list_open(session_text)` — адаптер вернёт незакрытые задачи, упомянутые в сессии (дедуплицированные). Пустой список → фаза завершена молча.

2. **Найти коммиты.** Один общий `git log --since="<начало сессии>" --pretty=format:'%H %s'` (граница сессии: по времени старта или последние ~6 часов, если старт неизвестен). Этот список — кандидаты для всех задач разом.

3. **Для каждой задачи — классификация на 3 ветки:**

| Ветка | Условие | Действие |
|---|---|---|
| **CLOSE** | Коммит(ы) явно реализуют acceptance задачи (summary + description). Артефакты совпадают. `ambiguous ≠ true`. | `close_task(id, "done", comment)`, где comment — список хешей релевантных коммитов. Доложить в финальной сводке. |
| **SKIP** | Коммитов с этой задачей нет, или коммиты нерелевантны (затронули соседнее, не closure). | Молча оставить open. **Не** упоминать в сводке. |
| **ASK** | Часть acceptance реализована / неоднозначно / `ambiguous = true` / задача из нескольких пунктов, сделана только часть. | В Confirm-поток Phase 1 отдельным пунктом с label `{id}: закрыть?` и description = summary задачи + список релевантных коммитов + причина сомнения. |

4. **Семантическая сверка (CLOSE vs ASK).** Перед классификацией CLOSE — прочитай `description` задачи (особенно блок «Acceptance», если есть). Если в description ≥2 явных пункта (numbered list, чеклист) — задача multi-part: CLOSE только если **все** пункты покрыты коммитами; иначе ASK с явным разбором «сделано X из N пунктов».

5. **Защита от ложного срабатывания.** Сопоставление задачи с коммитом — только по точному совпадению task-id в commit message или явной семантике задачи. Коммит про смежную систему (другой префикс id) не путать с task-id трекера.

### Финальная сводка Phase 0

```
## Авто-закрытие задач

Закрыто: 2
- {id-1} (done) — commits ac341d21, 17d2ce66
- {id-2} (done) — commit 89a3b85f

В Confirm-потоке Phase 1: 1
- {id-3} — частично (сделан пункт A, пункт B отсутствует)

Оставлено open: N (коммитов нет или не closure)
```

Если `comment_persisted: false` (трекер не принял комментарий) — в строке задачи пометка `(commit-hash-запись — в этой сводке, трекер не поддерживает комментарии)`. Если задач не упоминалось — фаза пропускается молча.

## Phase 1: Actionable Extraction

Пройдись по всему разговору. Найди **все** объекты, которые порождают конкретное действие за пределами этой сессии — Decision, Insight, OpenQuestion, Task, Idea. Не выделяй типы в отдельные фазы: один объединённый список, фильтр одинаковый для всех.

**OpenQuestion обрабатывается здесь же** — это просто actionable-объект с маршрутом «трекер / напоминание». Не ищи нерешённые вопросы отдельным проходом.

### Главное правило: actionable-фильтр

Объект показывается, если проходит **оба** теста:

1. **Из объекта следует конкретное действие** — задача / запись в бэклог / правка файла / memory / напоминание человеку.
2. **Это действие ещё не выполнено в этой сессии** (нет соответствующего коммита, правки, записи).

Если хотя бы один тест проваливается — **не показываем**. Даже если объект интересный, красиво сформулированный или структурно важный.

### Insight-расширение (для не-Decision объектов)

Insight, наблюдение, паттерн — становятся actionable, **только если указывают на gap или ошибку** в работе. Фильтр-вопрос:

> «Если этот insight НЕ зафиксировать — что мы повторим или упустим в будущем?»

| Подтип Insight | Actionable? | Куда |
|---|---|---|
| «Мы делали Y, надо было Z» (correction) | ✅ | feedback memory или правка процесса |
| «Мы упустили W» (gap) | ✅ | review-задача в трекер или правка чек-листа |
| «Это работает по принципу P» (pattern) | ✅ только если P переиспользуется | правка skill / документации |
| «Оказалось, что X» (factual discovery) | ❌ | не показывать — derivable из источника |

Локальные insights, которые растворяются в результате самой сессии — **не показывать**.

### Маршруты действия

| Действие | Куда |
|---|---|
| Создать задачу с дедлайном/исполнителем | трекер (через адаптер экземпляра) |
| Идея без срочности | backlog-файлы вашего инстанса (бизнес / продукт / идеи) |
| Изменить файл проекта | прямая правка в git (без отдельного предложения) |
| Изменить моё (Claude) поведение в будущем | memory (feedback или факт) |
| Спросить конкретного человека | напоминание (показать, не записывать) |

### Лестница мест: где правило живёт

Перед классификацией пункта в `Memory` — **обязательная** лестница мест по убыванию специфичности. Если правило применимо к конкретному артефакту, оно живёт **там**, не в memory. Memory — последнее прибежище, не первое.

| # | Куда | Триггер |
|---|---|---|
| **0** | **Конкретный артефакт: spec.md / код / комментарий в скрипте** | Правило про конкретный endpoint API / конкретный workaround / конкретный invariant. Если правило enforce'ится в строке кода или абзаце spec — туда же |
| 1 | Промпт продуктового агента | Правило про поведение конкретного агента |
| 2 | Инструкция Claude Code skill (`.claude/skills/*/SKILL.md`) | Правило про поведение конкретного skill |
| 3 | `agent-design-principles.md` §A или §B | Правило про класс компонентов (все продуктовые агенты §A / все Claude Code skills §B) |
| 4 | `operating-principles.md` | Универсальный принцип работы со знаниями |
| 5 | `CLAUDE.md` | Корневая инструкция, маршрутизация, обязательные шаги перед действиями |
| 6 | Memory | Только если ничего из 0–5 не подходит |

**Прогон обязателен.** Для каждого кандидата на memory — пройти 0→6 и явно зафиксировать, на каком уровне правило приземляется. Если уровень 0–5 подходит → пункт идёт туда (правка файла, не запись в memory).

**1-question test перед memory:** «**Где это правило ENFORCE'ится?**»
- Если в spec / коде / промпте / skill — **туда же, не в memory** (уровень 0–2).
- Если в общей дисциплине Claude без конкретного артефакта — **memory** (уровень 6).

**Обязательный dup-check перед созданием memory:** grep существующих memory-файлов по ключевому слову темы. Если существующий memory покрывает тему — **расширить его**, не создавать новый.

Антипаттерн: «memory как путь наименьшего сопротивления» — Write одной строкой проще, чем правка skill / principles / spec. Этот антипаттерн **запрещён**.

### Memory — что туда всё-таки попадает

После прогона лестницы memory остаётся для:
1. **Профиль пользователя** — роль, предпочтения, контекст (не выводится из файлов).
2. **Факты о внешних системах** — id очередей/досок трекера, пути облачного хранилища.
3. **Кросс-доменный feedback** — поведение Claude, которое **не привязано** к конкретному skill/агенту/принципу (если привязано — на уровни 1–4).

**Обязательный чеклист перед предложением memory** (после успешного прохода лестницы):
- [ ] Это нельзя вычитать из файлов проекта?
- [ ] Это не конфигурация в коде/скрипте?
- [ ] Это не fix/workaround?
- [ ] Это не дублирует существующее memory?
- [ ] Это профиль пользователя / факт о внешней системе / кросс-доменный feedback?

Если хотя бы один ❌ — не memory, вернуться на лестницу.

### Внутренний прогон фильтра — по принципу Signal Density

Применяется Принцип Signal Density: каждое слово в выводе несёт управляющий сигнал. Подтверждение «✅ всё ок» — не сигнал, а шум. Отчёт о работе фильтра — тоже шум.

Фильтр прогоняется по каждому кандидату молча. В вывод попадает **только то, что прошло фильтр**:

| Результат прохождения | След в выводе |
|---|---|
| Все ✅ — кандидат прошёл | Формулировка пункта в основном списке. |
| Хоть один ❌ — отклонён | Молча отфильтрован. **Не выводить** в чат. |
| Пограничный — Claude не уверен | Пункт в основном списке с пометкой `⚠️` и одной строкой сомнения. |

**По запросу пользователя** («что было отфильтровано?», «покажи скрытые») — Claude раскрывает список отклонённых с причинами. До запроса — молчание. Это default-off enforcement-журнал.

### Разделение на Auto и Confirm

После прогона actionable-фильтра каждый пункт классифицируется по одной из двух веток:

| Ветка | Когда | Действие |
|---|---|---|
| **Auto** | Уверен в пункте: формулировка ясна, маршрут очевиден, риск ошибки низок | Выполнить молча, без вопроса. В сводке доложить «сделано» |
| **Confirm** | Не уверен: пограничная формулировка, риск дубля, спорная категория, **или это memory** | Спросить через AskUserQuestion перед записью |

**Memory всегда в Confirm** — высокая цена ошибки (memory попадает в каждую будущую сессию, переучить дороже, чем подтвердить).

Все остальные ветки (трекер / бэклог / правка файла / напоминание) — по умолчанию **Auto**, переходят в Confirm только при пограничности (`⚠️` пометка после фильтра).

### Auto-поток

Уверенные пункты выполняются молча в порядке их появления. После выполнения — короткий отчёт:

```
## Actionable Extraction — выполнено

✅ Бэклог (продукт): [формулировка]
✅ Трекер {id}: комментарий добавлен
✅ Maintenance log: дополнен post-scriptum
```

Без обсуждения, без подтверждения, без диалога. Если пользователь захочет откатить — он скажет, я сделаю revert.

### Confirm-поток

Пограничные пункты + все memory — **до выполнения** прогоняются через AskUserQuestion. Каждый пункт = одна опция, multiSelect.

**Лимиты AskUserQuestion:** 2–4 опции на вопрос. Если пунктов в Confirm-потоке:
- **2–4** → один вызов с multiSelect
- **5+** → серия вопросов по ≤4 (memory приоритет, потом пограничные)
- **1** → текстовый вопрос «Записать?», ждать ответ
- **0** → шаг пропускается

**Формат опции:** `label` ≤5 слов (тип + краткая формулировка), `description` = полный текст пункта + причина пограничности (для `⚠️`). Header — `Подтвердить`, вопрос — `Какие пункты записать?`.

Из ответа взять отмеченные label'ы, выполнить только их. Не отмеченные — пропустить молча. «Other» с текстом — обработать как уточнение/правку.

### Финальная сводка

После Auto + Confirm выполнения — единая сводка:

```
## Actionable Extraction — итог

Сделано автоматически: 3
- Бэклог (продукт): [формулировка]
- Трекер {id}: комментарий
- Maintenance log: дополнен

Подтверждено: 1
- Memory (feedback): [содержание]

Пропущено: 1 (не отмечено пользователем)
```

Если ничего не было — «Всё actionable из сессии уже выполнено в коммитах/правках.»

### Целевая reject rate

Reject rate <30%. Если пользователь отклоняет ≥30% предложений — фильтр настроен слабо, в Phase 2 (самооценка) это отметить и подкрутить в следующей итерации skill.

## Phase 2: Самооценка качества AI-взаимодействия

После Phase 1 — оценить сессию по 5 метрикам качества AI-взаимодействия. Это **самопроверка**, не отдельная задача — занимает 30 секунд.

**Вывод — только сигнал (Signal Density):** в чат печатаются **только метрики с ⚠️ / ❌** — строка «метрика: значение — ремарка в 1 фразу». Все ✅ → одна строка «Качество сессии — высокое». Полная таблица — по запросу пользователя.

**Метрики и правила оценки:**

| Метрика | ✅ | ⚠️ | ❌ |
|---|---|---|---|
| Покрытие | Содержательная сессия → мостики созданы (артефакт + задача) | Создан только один тип мостика | Содержательная сессия без мостиков (потеря) |
| Связность | Каждый артефакт/задача имеет ≥ 1 явную связь (cross-ref, тег, ссылка) | Часть артефактов изолирована | Артефакты-сироты, никаких связей |
| Возврат | В сессии реально использовали ранее созданные артефакты | — | Не применимо (если сессия не требовала возврата) |
| Точность | Возвраты к артефактам давали нужный контекст без переспроса | Пришлось переспрашивать частично | Артефакт нашли, но не помог — переспросили заново |
| Precision Phase 1 | Reject rate <30% — actionable-фильтр работает | 30–50% — фильтр настроен слабо, в следующей сессии быть строже | >50% — фильтр сломан, нужна правка skill |

**Антипаттерн:** не подменять реальную оценку штампом «всё хорошо». Если сессия была шумной без артефактов — честно ❌ по покрытию.

## Phase 3: End of Day (автоматический)

После Phase 2 — **обязательно** выполнить End of Day. Не спрашивать — делать.

1. **Git commit** — закоммитить все изменения сессии (разбить на смысловые коммиты).
2. **`/kh-check`** — инкрементальная валидация изменённых файлов.
3. Автофиксы из kh-check — закоммитить отдельно.
4. **Сборка session-веток** — по положению рабочей копии:
   - **Рабочая копия на `main`** (основная установка): `git fetch`, затем
     `git branch -r --no-merged main | grep 'session/'`. Каждую ветку — по §28:
     сливается fast-forward/без конфликтов и меняет только документы →
     вычислимо-обратимое, слить самому и удалить с remote
     (`git push origin --delete session/<тема>`), доложить в сводке «слито: …».
     Конфликт или спорное содержание → не решать силой, показать пользователю.
   - **Рабочая копия в `session/*`-ветке** (облачная/выездная сессия): запушить
     свою ветку на remote и назвать её имя пользователю. В `main` из такой
     сессии не пушить — merge делает основная установка.
   - Remote недоступен (нет сети/токена) → шаг пропустить, назвать это в сводке.

---

## Завершение

После всех фаз — заверши коротко и тепло (1–2 предложения). Не шаблон — по-партнёрски, исходя из того, что реально произошло в сессии.

## Edge Cases

| Ситуация | Действие |
|----------|----------|
| Ничего значимого не произошло | «Ничего не фиксируем?» — если да, пропусти Phase 1, но Phase 3 (End of Day) всё равно выполни |
| Пользователь говорит «быстро закрываем» | Только Phase 1 + Phase 3, пропусти Phase 2 (самооценка) |
| Сессия была про конкретную задачу трекера | Предложи обновить статус/комментарий задачи (в составе Phase 1) |
| Изменений в git нет | Пропусти git commit в Phase 3, но /kh-check всё равно запусти |
| Трекер не подключён (нет `tracker:` в конфиге) | Phase 0 пропускается молча; остальные фазы — как обычно |
