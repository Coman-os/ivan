# /kh-check — Инкрементальная валидация Knowledge Hub

## Назначение

Быстрая проверка **только изменённых и новых** `.md` файлов за период. Работает за 1–2 минуты и ловит проблемы до того, как они накопятся. Встроена в End of Day workflow (`/close-session` Phase 3).

## Конфиг экземпляра (контракт вариативности)

Часть проверок читает **таксономию документов экземпляра** — что различается между клиентами (типы документов, папки, обязательные поля, статусы). База несёт универсальные структурные проверки; таксономию даёт экземпляр.

**Разрешение конфига (в начале):**
1. Найди инстанс-конфиг: единственный `*/.sync-config/sync-config.yaml`, секция `kh:`.
2. `kh.doc_taxonomy_ref` → документ таксономии (таблица `Тип | Папка | Обязательные поля | Допустимые статусы`). **Нет секции / файла** → Проверка A работает в **универсальном режиме** (наличие таблицы метаданных ИЛИ frontmatter + поле «Назначение»), без сверки типа по папке.
3. `kh.meeting_summary_source` (опционально) → спец обязательных секций выжимок для Проверки D. **Нет поля** → Проверка D **пропускается молча** (выжимки не авторятся вручную в этом экземпляре).

Все обращения к «типам документов экземпляра» идут через `kh.doc_taxonomy_ref`, не через захардкоженный список.

## Алгоритм

### Шаг 1: Получить список изменённых файлов

**Период по умолчанию:** вчера + сегодня (последние 2 дня). Если пользователь указал дату — использовать её.

```bash
# Незакоммиченные .md файлы (staged + unstaged + untracked)
git diff --name-only HEAD -- '*.md'
git diff --name-only --cached -- '*.md'
git ls-files --others --exclude-standard -- '*.md'

# ВСЕ .md файлы из коммитов за период (по умолчанию — 2 дня)
git diff --name-only $(git log --since="2 days ago" --format=%H | tail -1)^..HEAD -- '*.md'

# Если указана конкретная дата (YYYY-MM-DD):
# git diff --name-only $(git log --since="YYYY-MM-DD 00:00" --until="YYYY-MM-DD 23:59" --format=%H | tail -1)^..HEAD -- '*.md'
```

Объединить результаты, убрать дубли. Если файлов 0 → `✅ Нет изменённых .md файлов`.

**ВАЖНО:** Коммит ≠ валидация. Проверять все файлы из коммитов за период.

### Шаг 2: Для каждого файла — проверки

#### Проверка A: Метаданные (Consistency Checker)

Прочитать первые 20 строк файла. Определить тип по таблице из `kh.doc_taxonomy_ref` (таксономия экземпляра).

**ОБЯЗАТЕЛЬНО: для каждого файла пройти чеклист явно, поле за полем.** Для найденного типа — из таксономии взять список обязательных полей и допустимых статусов.

**Универсальный режим** (нет `kh.doc_taxonomy_ref`): проверить только, что у файла есть **либо** таблица метаданных (`| Параметр | Значение |`), **либо** YAML frontmatter (skill/шаблон), и что заполнено поле «Назначение» (sub-check A1). Тип по папке не сверять.

**Fallback** (таксономия есть, но файл не попадает ни под один тип) → `⚠️ Неизвестный тип документа — сверить с таксономией экземпляра`.

**Для каждого поля:** поле присутствует? значение из допустимых? формат верный (таблица, не blockquote)?

**Проверить согласованность:** emoji в заголовке ↔ статус в таблице, версия в заголовке ↔ версия в метаданных.

**НЕ писать «метаданные есть» без явной сверки каждого поля.**

##### Sub-check A1: Поле «Назначение» (карточка файла)

**Применяется к:** всем .md файлам, кроме исключений.

**Исключения:** `node_modules/`, `.git/`, `.claude/`, `__pycache__/`, `legacy/`, `archive/`, `versions/`, `README.md`, `CHANGELOG.md`, `SETUP.md`, `INSTANCE.md`.

**Что проверять:**
1. Поле `| Назначение | ... |` присутствует в таблице метаданных (первые 25 строк).
2. Содержание: 1–3 предложения, ≤100 слов.
3. Самодостаточность: понятно без чтения тела файла, нет `см. <ссылка>` вместо формулировки.
4. Не дублирует H1-заголовок дословно.

**Шаблоны допустимых формулировок:**
- README/ARCHITECTURE: `Навигационный индекс <папка>: <что в ней лежит>.`
- Журнал/changelog: `Append-only журнал <предмет>: <что фиксируется>.`
- Выжимка встречи: `Выжимка встречи <тип> от YYYY-MM-DD: <тема>.`

**Вердикт:**
- Поле есть, формулировка осмысленная → ✅
- Поле отсутствует → ⚠️ предложить добавить (по шаблону, если тип попадает)
- Поле есть, но >100 слов / содержит ссылки / повторяет H1 → ⚠️ переформулировать
- Антипаттерны («Содержит правила», «См. главу 3») → 🔴 переписать

#### Проверка B: Размещение (Decision Tree)

По context-distribution-rules.md:

1. **Файл в правильной корневой области?** — платформа (`coman-os/`) vs overlay экземпляра (контент клиента). Конкретные области — из placement-дока экземпляра.
2. **Файл в правильном подразделе?** — Knowledge Core vs Operations, система vs продукт.
3. **Если новый файл** — пройти Decision Tree и подтвердить размещение.

#### Проверка C: Дублирование контента (SSOT Check)

По rules.md → «Ссылайся, не повторяй»:

1. **Grep ключевые определения** из файла — типологии, списки статусов, классификации.
2. **Найти дубли** — те же определения в других файлах.
3. **Если дубль найден** — рекомендовать: оставить в SSOT, заменить ссылкой.
4. **Для промптов агентов** — проверить наличие секции `## Dependencies (SSOT)`.

#### Проверка D: Полнота выжимки встречи (Meeting Sections Check)

**Config-gated.** Применяется **только если** задан `kh.meeting_summary_source` — к файлам в папках `*/meetings/`.

1. Из `kh.meeting_summary_source` взять спец обязательных секций выжимки экземпляра (какие `## N.`/приложения требуются по типу шаблона).
2. Прочитать шапку файла — найти тип шаблона (обычно строка `> **Template:** <тип>`).
3. Сверить наличие требуемых секций (grep `## N.` / `## Appendix X` / `## Приложение X`).
4. **Вердикт:** все секции есть → ✅; отсутствуют → ⚠️ с перечислением; нет строки Template → пропустить (файл не сгенерирован по шаблону).

**Нет `kh.meeting_summary_source`** → проверка пропускается молча (в этом экземпляре выжимки не авторятся вручную / нет спецификации секций).

#### Проверка E: README актуальность (Navigation Index Check)

**Применяется к:** каждой папке, в которой были изменены/добавлены/удалены .md файлы.

По document-lifecycle.md → README:

1. **Папка содержит README.md?** Нет → создать индекс всех .md файлов папки. Да → п.2.
2. **Все .md файлы папки есть в индексе?** (кроме самого README.md). Нет → добавить строки: прочитать первые 20 строк, извлечь Статус и Обновлён; нет метаданных → `❓ No metadata`; описание = H1. Подпапки → одна строка `subfolder/` + количество документов.
3. **Нет «мёртвых» ссылок?** (файлы в индексе, которых нет в папке) → удалить строки.
4. **Статусы и даты в README совпадают с метаданными файлов?** Расхождение → обновить строку.
5. **Формат README корректен?** (таблица: Документ, Статус, Описание, Обновлён).

**Вердикт:** всё совпадает → ✅; расхождения → ⚠️ (автофикс при ≥85% уверенности); README отсутствует → 🔴 (автосоздание).

#### Проверка F: Status Transition Check

**Применяется к:** файлам типов Exploration, Experiment, Research, Методология (по таксономии экземпляра).

Проверяет, соответствует ли текущий статус документа его содержимому.

1. **Exploration со статусом 🚧 Draft:** grep `## Выводы`, `## Инсайты`, `## Экшен`. Все три → ⚠️ «критерии Complete выполнены, предложить → ✅ Complete».
2. **Experiment со статусом 🧪 Hypothesis:** grep `## Результаты`, `## Выводы`, `## Решение`. Все три → ⚠️ «→ ✅ Concluded».
3. **Research со статусом 🚧 Draft:** grep `## Выводы` + заполненность поля Источник. Оба → ⚠️ «→ ✅ Complete».
4. **Методология experimental:** grep ссылок на кейсы/пилоты/внедрение. Есть → ⚠️ «возможно, готова к stable, проверить вручную».

**Автофикс (≥85%):** только Exploration Draft → Complete (все три секции непустые). Остальное — human-in-loop.

#### Проверка G: Skill Map Drift

**Применяется к:** всегда, если в diff есть файлы `.claude/skills/*/SKILL.md` (созданы / удалены / переименованы).

По skill-capabilities-map.md:

1. **Собрать фактический список skills:**
   ```bash
   ls -1d .claude/skills/*/ | xargs -n1 basename | sort
   ```
2. **Извлечь skills, упомянутые в карте** — grep в §1 Decision Tree + §3 Цепочки + §5 Антипаттерны.
3. **Diff:** skills в ФС, но не в карте → 🔴; skills в карте, но не в ФС → 🔴.
4. **Счётчик в шапке карты** ↔ фактическое количество.
5. **Поле «Обновлён»** ≥ даты последнего изменения `.claude/skills/`.

> Платформенные (`cmn:`) скилы регенерируются — их карта приезжает из базы. Overlay-скилы экземпляра в эту карту не входят (их реестр — `.claude/skills/README.md`). Проверять на дрейф — соответствующий реестр.

**Root cause при drift:** нарушено правило обновления карты после создания/удаления skill. Блокирующее — не закрывать сессию с untracked skills.

#### Проверка H: Folder Bloat Check

**Применяется к:** каждой папке, в которой менялись .md файлы.

По context-distribution-rules.md, синхронно со сверкой индексов папок:

1. Подсчитать .md на верхнем уровне папки (не рекурсивно), исключая `README.md` и файлы на `_`.
2. **Skip для хронологических архивов** (`meetings/` и подобные — навигация через `history-log.md`).
3. **Threshold:** < 10 → ✅; ≥ 10 → 🔴 folder bloat: декомпозиция на подпапки по смысловым темам (≥3 файла в каждой). Наличие подпапок не освобождает.

**Вердикт:** < 10 → ✅; ≥ 10 → 🔴 (запустить полный аудит структуры).

### Шаг 3: Root Cause анализ

Если Проверка A нашла отсутствующее поле — **не останавливайся на файле**. Трассируй до источника:

1. Определи, по какому шаблону создан файл.
2. Проверь, есть ли пропущенное поле в шаблоне.
3. Поле **отсутствует в шаблоне** → root cause = шаблон (один fix закроет будущие файлы).
4. Поле **есть в шаблоне**, но не заполнено → root cause = генерация (заполнить из доступных источников).

**Принцип:** Чинить причину, а не следствие. Один fix в шаблоне > десять fix в файлах.

### Шаг 4: Отчёт

```markdown
## KH Check Report (YYYY-MM-DD)

**Проверено файлов:** N

### Результаты

✅ [файл1.md] — OK
⚠️ [файл2.md] — Метаданные: отсутствует Owner
⚠️ [файл3.md] — Размещение: содержит переиспользуемые знания → платформенная область?
🔴 [файл4.md] — Дублирование: определяет «типы документов», уже определены в SSOT

### Автофиксы

Очевидное (≥85% уверенности) — исправить сразу. Неочевидное — спросить.
```
